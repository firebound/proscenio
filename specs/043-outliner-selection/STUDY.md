# Spec 043: Outliner selection correctness

Make the Proscenio Outliner reflect the real scene: highlight the row the user clicked even under filter/sort, follow a selection made in the viewport, never crash on a row pointing at a freed or view-layer-absent object, and drop the redundant second search field.

## Scope

- **Follow the viewport selection.** Selecting an object directly in the 3D viewport does not move the Outliner highlight; it keeps showing the previously clicked row. No handler maps `view_layer.objects.active` back to `active_outliner_index`.
- **Highlight the row the user clicked (identity, not position).** The active-row index is written by position in the raw `bpy.data.objects` order, but the list renders a filtered + category-sorted view, so the highlight lands on the wrong visual row whenever the two orders diverge (finding F-06).
- **Never crash on a stale row.** The list is sourced from `bpy.data.objects`, which still contains blocks left after a delete/undo; clicking such a row calls `obj.select_set(True)` unguarded and raises `RuntimeError: Object '...' cannot be selected because it is not in View Layer`.
- **Drop the redundant search bar.** Two search fields exist (the Proscenio `outliner_filter` text box and Blender's native UIList "Filter by Name"); the native one is enough (finding F-04).
- **Favorites do not reorder to the top** (finding F-01, low severity) - decide whether to honor the "pins to the top" promise the description makes, or correct the copy.

Originally out of scope but folded into this PR: left-aligning the row labels (a spec 036 item, landed here since this PR already restructured these `draw_item` rows). The parent-nested hierarchy tree with expand/collapse was dropped (no native Python tree widget; see [`dropped.md`](../dropped.md) `outliner-hierarchy-tree`).

## Study

### Surface notes

**The highlight is computed in the wrong coordinate system (F-06).** `panels/outliner.py:150-158` binds the `template_list` to `scene.proscenio.active_outliner_index` over `bpy.data` `objects`. On click, `operators/selection.py:58` calls `_sync_active_index(context, "active_outliner_index", bpy.data.objects, self.obj_name)`; `_sync_active_index` (`selection.py:153-167`) walks `bpy.data.objects` in iteration order and writes the first index whose `candidate.name == target_name`. That index is correct only if the UIList draws rows in `bpy.data.objects` order - but `filter_items` (`outliner.py:86-124`) returns a `flt_neworder` that re-sorts every row by `(category rank, name.lower())` (`outliner.py:120-124`) and a `flt_flags` that hides non-Proscenio objects, the favorites-only set, and rows failing the text filter (`outliner.py:104-119`). So `_sync_active_index` already matches by *name* (it is not a naive positional write), but it matches against the wrong sequence: it returns the index into the unfiltered/unsorted collection, while the UIList's `active_index` is interpreted against the *displayed* order. The highlight therefore lands on a different visible row whenever sort or filter reorders things - which is the normal case the moment there is more than one slot or any text in the filter.

The honest fix is to make the operator compute the index the same way the UIList does. `active_index` on a `template_list` is an index into the *source collection* (`bpy.data.objects`), not into the displayed order - Blender maps source index → display position internally through `flt_neworder`. Re-reading the Blender UIList contract: the `active_propname` index is the index into the original `CollectionProperty`, and `flt_neworder[orig_i]` gives that item's visual slot. That means `_sync_active_index`'s by-name match into `bpy.data.objects` is *almost* right - the subtle bug is that when a row is filtered *out* (`flt_flags[i] == 0`), pointing `active_index` at it highlights nothing visible, and when two objects share a name across data-blocks the first wins regardless of which is shown. The end-to-end mapping to verify by experiment before coding: (1) confirm `active_index` is interpreted against the source collection, not the reordered view (the F-06 finding's wording "active-row highlight can land on a different visual row" suggests it is *not*, or that an older Blender interpreted it positionally - this must be reproduced, not assumed); (2) if it is source-indexed, the remaining work is to skip filtered-out matches and prefer the object actually in the view layer; (3) if it is display-indexed, `_sync_active_index` must run the same `(rank, name)` sort + filter and return the display slot. This uncertainty is real and is the single most important thing to nail down first - the fix shape differs completely between the two cases.

**No handler follows the viewport selection.** There is no code path from `view_layer.objects.active` back to `active_outliner_index`. The infrastructure to add one already exists and is already running: `properties/_handlers.py:69-100` defines `on_depsgraph_update`, a `@persistent` `depsgraph_update_post` handler registered at `properties/__init__.py:83-84`, today doing one job - nulling a dangling `active_armature` pointer. Extending this handler (rather than adding a second one) is the cheap path: read `scene.view_layer.objects.active`, map its name through the same identity→index logic above, and write `active_outliner_index` only when it actually changed (an unconditional write every depsgraph tick risks redraw churn and a write-during-draw warning). The handler is already wrapped in a broad `except Exception` for draw-cycle safety (`_handlers.py:97-100`) and already calls `_tag_view3d_areas_redraw()` (`:103-104`), so the redraw plumbing is in place. Cost concern to confirm: `depsgraph_update_post` fires very frequently (every transform, every frame change); the added work must be a cheap guarded comparison, and it must early-out when the active object is unchanged or is not a Proscenio-relevant object (the same `_outliner_category_rank == 9` rows the list hides). The shared identity-mapping helper from the F-06 fix should be reused here verbatim so the two paths cannot drift.

**The stale-row crash, and its blast radius.** Click path: `outliner.py:71-77` (`row.operator("proscenio.select_outliner_object", ...)`) → `selection.py:53-59` (`execute`) → `select_named_or_warn` (`select.py:84-113`) → `select_only` (`select.py:23-35`). `select_only` does `obj.select_set(True)` at `select.py:34` with no guard. When the row points at an object that is in `bpy.data.objects` but not linked into the current view layer (the classic post-delete / post-undo state, because the list is sourced from `bpy.data` not the scene), `select_set(True)` raises `RuntimeError: ... not in View Layer`. Contrast `restore_selection` (`select.py:51-61`), which already wraps every `select_set` / active-assignment in `contextlib.suppress(RuntimeError, ReferenceError)` precisely for this case.

The blast radius rules out the obvious shortcut: `select_only` is the shared deselect-all-then-select-one helper (its docstring lists five-plus callers: `select_issue_object`, `select_outliner_object`, `select_bone_by_name` via `select.py:88`, `create_ortho_camera`, `reproject_sprite_uv`, `create_slot`). Blanket-suppressing the `RuntimeError` inside `select_only` would silently change the contract for all of them - a slot or camera operator that *should* surface "this object cannot be selected" would now no-op quietly. So the guard belongs at the Outliner boundary, not in the shared helper. Two acceptable shapes: (a) in `PROSCENIO_OT_select_outliner_object.execute`, pre-check `self.obj_name in context.view_layer.objects` before delegating, and `report_warn` + `CANCELLED` otherwise - this is an explicit skip-and-warn, mirrors `select_named_or_warn`'s existing not-found warning, and keeps the shared helper untouched; or (b) add an opt-in `skip_if_not_in_view_layer` keyword to `select_named_or_warn` that the Outliner operator passes, leaving the default behavior (raise) for every other caller. (a) is the smaller change and is preferred; (b) is worth it only if spec 046's reusable list component will want the same guard at the helper level.

There is a second, deeper question behind the crash: *should stale rows appear at all?* The list is bound to `bpy.data` `objects` (`outliner.py:152-153`), which is why freed/undone blocks survive in it. Sourcing the list from `scene.objects` (or `view_layer.objects`) would mean the list only ever shows objects that can actually be selected, eliminating the crash by construction rather than guarding it. The trade-off: `bpy.data.objects` is a real `CollectionProperty` that `template_list` accepts directly; `scene.objects` is also a collection but its membership changes on link/unlink, and after an undo the set it exposes is the post-undo truth (arguably *more* correct than `bpy.data`). The risk is that `_outliner_category_rank` and `filter_items` are written against the `bpy.data.objects` shape and would need re-verification against `scene.objects` indexing - and the F-06 active-index mapping above is *also* sensitive to which collection backs the list, so this decision must be made *before* the identity fix, not after. Recommended posture: ship the explicit guard (a) as the safe minimum regardless, and evaluate the `scene.objects` source as a follow-up only if it does not perturb the rank/sort logic - do not couple the crash fix to a source-collection migration on the first PR.

**Dual search - the drawer is not the whole story (F-04).** `outliner.py:147-149` draws the Proscenio text field (`outliner_filter`) next to the favorites toggle. `filter_items` honors *both* that prop and the native `self.filter_name` (`outliner.py:95-99`), with the Proscenio bar winning when both are set (`flt_text = proscenio_text or native_text`, `:99`). Removing the visible drawer row (`:148`) is UI-only and leaves `filter_items` still reading `outliner_filter` - harmless but dead, since nothing can set the prop anymore. The clean removal is two coordinated edits: drop the `row.prop(..., "outliner_filter", ...)` draw *and* stop honoring `outliner_filter` in `filter_items` (collapse `:95-99` to just `native_text`). Leave the `outliner_filter` PropertyGroup field (`scene_props.py:468-475`) in place or remove it as a tidy-up - removing it is a registered-property change that affects saved files, so prefer to leave it defined-but-unused unless a wider prop sweep is happening. Net effect: one search field (Blender's native), the surprising "bar wins" precedence gone.

**Favorites do not reorder (F-01).** `filter_items` sorts purely by `(rank, name.lower())` (`outliner.py:120`); the favorite flag only feeds the favorites-only filter (`:115`), never the sort key. Meanwhile the property description (`object_props.py:253`, per F-01) and the QA doc both promise the star "pins this object to the TOP." This is a one-line divergence with two honest resolutions: either add favorite-ness as the primary sort key (`key=lambda i: (0 if is_fav[i] else 1, ranks[i], name)`), making the promise true, or correct the description + checklist copy to say "favorites survive the favorites-only filter" (which is what BL-OUTLN-08 already observed: "The row does not move to the top"). Low severity either way; the sort-key change is small and makes the existing copy correct, so it is the marginally better option but is genuinely optional.

### Research notes

Blender's own Outliner is the precedent for both the highlight and the view-layer guard. Native Outliner sync is bidirectional by construction because it is a C-side editor bound to the view layer, not a Python `UIList` over `bpy.data` - which is exactly why Proscenio's `bpy.data`-sourced re-implementation has to rebuild that sync by hand and inherits the stale-block problem the native editor never has (the native Outliner's "Blender File" display mode is the only one that shows orphaned data, and it does not let you select-into-viewport from there). The UIList `flt_neworder` / `flt_flags` filtering contract (the `bitflag_filter_item` mechanism used at `outliner.py:119`) is the documented Blender API for custom-filtered lists; the open question above is purely *which* index space `active_index` lives in, and the Blender source/docs should settle it before the F-06 fix is coded. No third-party precedent is needed.

### Verdict summary

**5 now, 1 defer.** The recommendation is three PR-sized chunks. **PR 1 (the crash, shippable alone):** the explicit view-layer guard at `PROSCENIO_OT_select_outliner_object` plus a headless test for the skip-and-warn - this is the only hard crash and must not wait on the index investigation. **PR 2 (correct highlight):** first reproduce which index space `template_list.active_index` lives in (the load-bearing unknown), then fix `_sync_active_index` to skip filtered-out matches and prefer the view-layer object, factor the identity→index mapping into a shared helper, and extend the existing `on_depsgraph_update` handler to follow the viewport selection through that same helper - both halves verified together since they share the mapping, with a measured early-out on the hot callback. **PR 3 (the search + favorites cleanup):** remove the Proscenio search drawer and stop honoring `outliner_filter` in `filter_items` in one coordinated edit, and either add the favorite sort term or correct the "pins to top" copy. Defer the `scene.objects` source migration until the identity fix is stable, since it would otherwise widen PR 2 into a source-collection change that the rank/sort logic is sensitive to.

**Cross-spec coordination.** Spec 036 left-aligns the same `draw_item` rows (`outliner.py:70-84`); sequence so 043's PRs do not collide with 036's row-layout edit - ideally land 043 PR 1 (operator-only, does not touch `draw_item`) freely, and coordinate PR 3's drawer removal with 036's row work since both edit `outliner.py`. Spec 046 builds the reusable list component and explicitly needs the same identity-based active-index fix (its STUDY notes a prior Skeleton-panel selection-sync cost); the shared identity→index helper produced in 043 PR 2 is the thing 046 must consume rather than re-derive - keep it in a place 046 can import.

**Unresolved decision.** The one thing this study could not settle from a code read alone is *which coordinate space `template_list.active_index` is interpreted in* - source-collection index vs displayed (`flt_neworder`) slot. The F-06 finding's wording implies the highlight is mis-landing, but Blender's documented contract says `active_index` is a source-collection index (which would make the current by-name match nearly correct). This must be reproduced in a running Blender before PR 2 is coded, because the fix is materially different in each case. It is flagged as the first task in PR 2.
