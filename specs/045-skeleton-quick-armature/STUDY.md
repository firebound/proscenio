# Spec 045: Skeleton, Quick Armature and Animation fixes

Fix the Animation panel so it respects the picked armature, settle what "cancel" means in the Quick Armature modal, and clean up the Skeleton chrome.

## Scope

- **Quick Armature cancel-vs-confirm.** Esc and Enter feel identical because, on the data, they nearly are: the empty-rig sweep runs on both paths and the only difference is the return code plus a one-word report verb. Decide by repro what "cancel" should mean once a bone is authored, then make the labels read differently from confirm - ideally changing once the first bone exists.
- **Animation panel armature (bug).** The "assign action" path picks the first armature in the scene and only warns when there is more than one; it never reads the Skeleton picker and never warns when nothing is picked. Rework it to read `scene.proscenio.active_armature` and cancel-with-a-warning when the picker is empty - or remove the write action entirely, since the panel is framed read-only.
- **Chrome (all small).** Mark "disconnected" child bones in the bone list (today only "connected" / "relative" show); show the active armature name in the Skeleton header via a `draw_header` override; rename the "Armature" subpanel to "Active Armature"; remove the leftover 3D-viewport-header chord append now that the status bar carries the same hints.

Out of scope, tracked as their own backlog items (mentioned here only so the reader knows where the line is): **qa-rotation-mode** (Euler-Y vs quaternion authoring choice plus a safe swap) and **qa-quickarm-interaction-revision** (the modifier-tap vocabulary rethink plus viewport pick-parent). Neither is touched by this spec.

## Study

### Surface notes

**The Esc "bug" is most likely a labelling / semantics question, not a broken cancel - but it needs a repro to be sure.** The dispatch is in `operators/armature/quick_armature.py:236-240`: `_is_exit_event` (`:843-844`, Esc / RMB press) computes `cancelled = _drag_head is None and _last_bone_name == ""` and calls `_exit(context, cancelled=cancelled)`; `_is_confirm_event` (`:847-848`, Return / Numpad-Enter) calls `_exit(context, cancelled=False)`. The decisive detail is what `cancelled` actually controls. In `_exit` (`:803-822`) the flag only selects the return value (`{"CANCELLED"}` vs `{"FINISHED"}`) and the report verb (`"cancelled"` vs `"confirmed"`, `:820-821`). It does **not** drive rig removal. The rig removal is `_sweep_empty_armature` (`:786-801`), called unconditionally from `_exit` at `:809`, and it removes the rig only when `_created_armature_this_session` is true **and** `len(armature.data.bones) == 0`. So:

- With nothing drawn, both Esc and Enter sweep the empty auto-created rig - the desired "cancel" outcome happens on both paths already.
- Once one bone is authored, neither Esc nor Enter removes anything - the bones survive. Esc and Enter genuinely do the same thing to the scene; only the toolbar report line differs by one word.

That matches the user report ("Esc and Enter seem to do the same thing") far better than "Esc does not cancel". So the most probable defect is twofold: (1) the chord cheatsheet labels Esc as "exit" and Enter as "confirm" (`operators/armature/_status_bar.py:46-47`), which read as near-synonyms and never change as bones accumulate; and (2) there is no destructive cancel - Esc after authoring keeps the bones, which may or may not be what we want. **The first study task is the repro** (bare Esc; Esc after one bone; Enter after one bone), checking the resulting scene against the report verb, to decide between two outcomes:

- *Labels-only* (cheaper, lower risk): keep the current data behaviour (Esc never deletes authored bones), and make the hints honest. Relabel the Return chord as "keep" / "finish" and the Esc chord as "exit"; while nothing is drawn, the Esc hint can read "cancel (discards empty rig)". This needs the chord layout to take session state.
- *True destructive cancel* (matches the backlog's literal wording "Esc cancels and removes the auto-created rig"): on Esc, sweep the whole auto-created `Proscenio.QuickRig` even when it has bones (but still never touch a user-picked target armature, which is the existing `_created_armature_this_session` guard). This is a behaviour change with real bug surface - a misfired Esc would delete a session's work - so it should only ship if the repro shows users expect Esc to throw the rig away.

The honest recommendation: do the repro, default to *labels-only* unless the repro clearly shows users want a destructive Esc, and in either case make the labels dynamic so the hint changes once a bone is authored. The dynamic part is the real fix to "they look the same".

**The chord labels are already partly dynamic, which shows the mechanism is in place.** `emit_chord_layout` (`operators/armature/_status_bar.py:23-47`) already swaps the connected / unparented wording based on `cls._default_chain` (`:33-38`). It reads class state off the operator type. Adding a session-state read (e.g. `cls._last_bone_name` or a bone count) to swap the confirm / exit wording is the same pattern - the function already takes the operator class, so no new plumbing is needed. The confirm / exit chords are the last two rows (`:46-47`).

**The Animation "assign action" is the clearest bug in the spec.** `operators/selection.py:96-132` (`PROSCENIO_OT_set_active_action`) builds `armatures = [o for o in context.scene.objects if o.type == "ARMATURE"]` (`:117`), warns only when `len > 1` (`:121-126`), then assigns to `armatures[0]` (`:127-131`) - it never consults the Skeleton picker and never warns when the picker is empty. This is wrong in exactly the way the Skeleton panel is careful to be right: that panel resolves its target through `scene.proscenio.active_armature` (the picker, `panels/skeleton.py:19-22`), which is the single source of truth per `core/armature/skeleton_target.py:27-41` (`resolve_skeleton_target` reads only the picker, returns `None` when unset). The operator-side setter is `operators/armature/skeleton_target.py` (`PROSCENIO_OT_set_active_armature`). The fix is to make the action operator read the same picker. The `bl_description` (`:101-104`) also advertises the wrong behaviour ("the first armature in the scene") and must change with it.

There is a design question underneath the bug. `panels/animation.py:39-40` documents the panel as a "Read-only summary of the actions the writer would emit", yet the actions UIList (`:17-36`) wires every row to this write operator via `row.operator("proscenio.set_active_action", ...)` (`:29-35`). Two coherent resolutions:

- *Keep the action, make it correct:* read `resolve_skeleton_target(context)`; if `None`, `report_warn` ("no armature picked - pick one in the Skeleton panel") and cancel; otherwise assign to the resolved object exactly as today (`animation_data_create()` then `.action = action`, `:128-131`). This keeps the convenience of clicking an action to preview it on the timeline and aligns the message vocabulary with the Skeleton panel's own "no rig picked" copy (`panels/skeleton.py:109`). Drop the multi-armature heuristic entirely - the picker disambiguates.
- *Remove the write, honour the read-only framing:* make each row a plain label / selectable index and delete `PROSCENIO_OT_set_active_action`, on the argument that action-to-armature assignment belongs wherever the armature itself is owned (Skeleton), not in a panel that calls itself a summary.

Recommendation: keep the action and make it correct. It is the lower-friction outcome for the animator (one click to audition an action), the picker removes the ambiguity that justified the original heuristic, and "read-only summary" is a stale docstring rather than a load-bearing contract. Findings F-67 / F-72.

**The bone-list "disconnected" flag is one branch, but it needs a definition decision.** `PROSCENIO_UL_bones.draw_item` (`panels/skeleton.py:30-65`) builds a `flags` list: it appends "connected" when `use_connect` (`:61-62`) and "relative" when `use_relative_parent` (`:63-64`), then joins them into a trailing label (`:65`). A bone is meaningfully "disconnected" when it has a parent but is not connected to it: `item.parent is not None and not getattr(item, "use_connect", False)`. The decision is whether to flag *every* unconnected child (honest but noisy - disconnected parenting is a legitimate, common rig topology) or only flag the ones that look like mistakes. There is no reliable "mistake" heuristic at the data level - a disconnected child is not wrong, it is a choice - so flagging every unconnected child is the only defensible rule. Recommendation: flag every child where `parent is not None and not use_connect`, and accept the label noise; it is strictly more information than today (which is silent for those bones). Root bones (no parent) get no connectivity flag, same as now.

**The Skeleton header active-name needs a `draw_header` override because `bl_label` is static.** `PROSCENIO_PT_skeleton` (`panels/skeleton.py:68-77`) sets `bl_label = "Skeleton"`, a class constant Blender cannot vary per redraw. Showing "Skeleton: <name>" needs a `draw_header` method that draws the label text itself. The panel already overrides `draw_header_preset` (`:83-84`) for the `?` help button, so adding `draw_header` sits alongside it cleanly. Two safety points: read the picked armature through `_explicit_target(context)` (`:19-22`), and guard against a deleted / unset target - when the picker is empty or the pointed-at object is gone, fall back to the plain "Skeleton" label rather than dereferencing a stale pointer. (Blender clears `PointerProperty` references on object deletion, so `_explicit_target` returning a freed datablock is unlikely, but the empty / `None` case is the common path and must read cleanly.) This is the same shape as the deferred `element-header-active-name` pattern the chrome backlog references for consistency.

**The subpanel rename is a one-line `bl_label` edit.** `PROSCENIO_PT_armature` (`panels/skeleton.py:123-127`) is `bl_label = "Armature"`; rename to "Active Armature". The `bl_idname` (`PROSCENIO_PT_armature`) and `bl_parent_id` wiring stay untouched - only the visible label changes - so nothing else has to move. The docstring (`:124`) and the in-body label `f"Armature '{target.name}' - {len(bones)} bone(s)"` (`:149`) already read fine; the body label can stay or be trimmed once the header carries the name, a cosmetic call to make during the change.

**Removing the viewport-header hints is a clean deletion.** The modal registers two icon-rich hint surfaces in `_register_handlers` (`quick_armature.py:739-758`): the STATUSBAR prepend (`:750-755`) and the VIEW3D_HT_header append (`:756-758`). The renderer for the viewport-header copy is `_draw_view3d_header_quick_armature` (`:904-917`). The status bar already carries the full chord vocabulary via `_draw_statusbar_quick_armature` (`:892-902`) using the identical `emit_chord_layout` call, so the viewport-header surface is pure duplication (finding F-38). The removal must be complete to avoid a leaked handler: drop the append branch (`:756-758`), the `_view3d_header_appended` ClassVar (`:136`), its double-invoke guard reference (`:163-164`), its teardown in `_unregister_handlers` (`:774-777`), its sweep in `_sweep_orphan_handlers` (`:942-945`), and the `_draw_view3d_header_quick_armature` function itself (`:904-917`). The double-invoke guard and the orphan sweep are the easy ones to miss; leaving them referencing a removed flag is harmless but leaving the append without the teardown would leak the header callback across reloads.

### Verdict summary

**7 now, 1 gate.** The work is one repro plus two small PRs. The Esc item is the only real uncertainty and it is sequenced repro-first: a single GUI session decides between the cheap labels-only outcome (recommended default - the chords read as synonyms and never change, which is the actual "they look the same" complaint) and the destructive-cancel outcome (gated on the repro showing users expect Esc to discard authored bones; it carries real bug surface so it does not ship on assumption). The Animation bug is unambiguous and headless-testable. The four chrome items are each a few lines and ride one GUI smoke pass. Recommended as two PRs: (1) the Animation picker fix with its headless test; (2) one batched Quick Armature + Skeleton chrome PR carrying the dynamic confirm / exit labels (after the repro), the disconnected-bone flag, the header active-name override, the subpanel rename, and the viewport-hint removal - all verified by a single GUI smoke pass over `BL-SKEL-*`, `BL-ANIM-01..03`, and `BL-SKEL-QUICKARM-01`. Whether a third PR is needed (the destructive cancel) is the one open decision, owned by the repro.
