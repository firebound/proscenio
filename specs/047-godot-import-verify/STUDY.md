# Spec 047: Godot importer verification and docs

Confirm the sprite manual-region pixel scaling with a test, fix the no-texture region edge case, and document two model quirks. Small spec, scoped to `apps/godot` plus a docs page.

## Scope

- Verify, with a headless test, that a sprite carrying a manual `texture_region` **and a texture** produces the right pixel `region_rect`. A code read confirms the multiplication is correct, so this is a confirmation, not a fix - unless the test surprises us.
- Fix (or consciously close) the **no-texture region edge case**: when a region is present but no texture resolves, the builder enables the region but leaves `region_rect` at `(0,0,0,0)`. A code read found nothing that fills it later, so the in-code comment promising a later fill is wrong. Cover the decided behaviour with a test.
- Document the `_001` name-collision suffix convention: colliding node names get a numeric suffix (Godot's own `add_child` behaviour), never a kind prefix, because animation tracks resolve their targets by name.
- Surface the Blender-vs-Godot multi-frame sprite preview difference on the Godot plugin doc page. It is inherent to the model, not a code bug; the authoring rule that keeps bounds matching (`quad_units = frame_px / ppu`) is already written in the fixtures README and only needs an import-side pointer.

## Study

### Surface notes

**The reported region "bug" is a false alarm on the with-texture path - confirmed.** `apps/godot/addons/proscenio/builders/sprite_builder.gd:60-72` reads the normalized `texture_region` (the `.proscenio` carries `[0,1]` values, the same convention as mesh UVs) and, when a texture is present, multiplies each component by the texture size before assigning `region_rect`: `Rect2(region[0]*tex_size.x, region[1]*tex_size.y, region[2]*tex_size.x, region[3]*tex_size.y)`. The mesh builder does the identical scaling for UVs at `mesh_builder.gd:77-85` (`uv_scale = sprite_tex.get_size()`, then `Vector2(u[0]*uv_scale.x, u[1]*uv_scale.y)`). Both are correct: Godot's `Sprite2D.region_rect` and `Polygon2D.uv` both want texture-pixel space, and both builders convert from normalized into pixels. There is no divergence between them and nothing to fix on this path. The headless test should pass on the first run; if it does not, the assertion is wrong before the code is.

**The real latent bug is the no-texture path.** The region block in `sprite_builder.gd:60-72` sets `region_enabled = true` and `region_filter_clip_enabled = true` unconditionally (lines 61, 64), but the `region_rect` assignment is nested inside `if sprite_tex != null:` (line 65). So when no texture resolves, the sprite ships with `region_enabled = true` and `region_rect` left at its default `(0,0,0,0)`. Godot's `Sprite2D` with an enabled region and a zero-area rect draws nothing - an enabled empty region is not the same as a full-texture sprite. The code comment at `sprite_builder.gd:54-59` rationalizes leaving the rect empty by claiming "the rect is filled in by the importer's real load," but that claim does not hold: see below.

**No code fills the rect later - the comment is stale.** `importer.gd:_import` (lines 63-109) is the only real load path. It builds the skeleton, loads the atlas (`_load_atlas`, lines 153-173), builds slots, calls `MeshBuilder.attach_elements` then `SpriteBuilder.attach_elements` (lines 89-90), populates animations, then immediately sets owners, packs the `PackedScene`, and saves it (lines 97-109). There is no post-build pass over the sprites, no second texture resolution, nothing that revisits `region_rect`. The texture the builder sees during `attach_elements` is the only texture it will ever see - the import order (`_get_import_order` returns 100, `importer.gd:37-44`) exists precisely so the PNGs are imported before the `.proscenio` bakes, so by the time `attach_elements` runs the texture should already resolve. The comment describes a fill-up that does not exist.

**When can `sprite_tex` actually be null in the real path?** `SpriteAttachUtil.resolve_sprite_texture` (`sprite_attach_util.gd:17-35`) tries, in order: the per-sprite `texture` path, a `<name>.png`-by-convention sibling, then the scene-wide `fallback_atlas`. It returns null only when all three miss - a genuinely missing texture file, a path typo, or a still-unresolved import (the order-100 guard makes the last unlikely but not impossible for a freshly added asset). In every one of those cases the sprite already renders wrong (no texture), but with a region present it now renders as an enabled empty region, i.e. fully invisible rather than a broken-but-visible placeholder. So the edge case degrades an already-degraded state. It is latent because the only sprite fixture (`effect`) has a texture and never triggers it.

**The headless test never exercises the edge case today.** `apps/godot/tests/test_importer.gd:87-132` (`_run_effect_checks`) is the only `Sprite2D` region coverage. It asserts `region_enabled` and `region_filter_clip_enabled` are true (lines 111-112) but never asserts the *value* of `region_rect`, and the `effect` fixture has a texture so the null branch is dead. `_build_character` (lines 326-344) passes `null` as the atlas to both builders, so under the headless harness `resolve_sprite_texture` already returns null for any sprite without a per-sprite or by-name PNG - meaning the harness is in fact already on the no-texture path for `effect`'s region, yet asserts only the flags. Two cases are missing: (1) a with-texture region asserting the scaled pixel `region_rect`, which needs a fixture whose sprite resolves a real texture of a known size; (2) the no-texture region asserting the decided behaviour.

**The `_001` suffix is Godot's, and the suffix-not-prefix choice is forced by name-based track lookup.** No Proscenio code writes a `_001` suffix - a grep across `apps/godot` finds none. Builders assign `node.name = element.name` verbatim (`sprite_builder.gd:35`, `mesh_builder.gd:57`, slot at `slot_builder.gd:43`); when two siblings collide, Godot's `add_child` auto-appends `_001`, `_002`, and so on. The reason this matters - and the reason the importer must never disambiguate by *prefixing* (e.g. `sprite_foo` / `mesh_foo`) instead - is that animation tracks resolve their targets by name: `animation_builder.gd:40` sanitizes `track.target`, then `find_child(target, ...)` resolves it for bone tracks (line 53), sprite_frame tracks (line 62), and slot_attachment tracks (line 80). A prefix would change the leaf name and break that lookup; a numeric suffix on a *colliding* node is acceptable because a unique name was never ambiguous to begin with. This is undocumented today and belongs in the Godot plugin reference next to the node-tree description.

**The multi-frame preview difference is already documented once, on the authoring side.** `packages/fixtures/README.md:135-136` ("Sprite quads (multi-frame)") states the model exactly: a `sprite` element renders in Godot as a `Sprite2D` showing one frame at its native pixel size (`region_px / hframes`), while Blender shows the whole authored quad, and the rule that keeps bounds matching is `w = frame_px / PIXELS_PER_UNIT` (i.e. `quad_units = frame_px / ppu`); pixel-exact Blender==Godot is not achievable for multi-frame sprites by design, the invariant is geometry/bounds, not pixels. That home is correct for fixture authors. The import-side reader of `docs/04-godot-plugin/index.md` (and the basic guide `docs/00-guides/00-basic/03-godot.md:25`, which says only "`Sprite2D` sprites slice their `region_rect` by `hframes`/`vframes`") gets no such caveat. The doc work is a short pointer on the Godot plugin page back to the authoring rule, not a re-derivation.

### Verdict summary

**Four rows, all now, one small PR plus a docs follow-up.** The reported region scaling "bug" is verified as a false alarm on the with-texture path by a code read of `sprite_builder.gd:60-72` against `mesh_builder.gd:77-85`; the work there is a confirming test, not a fix. The genuine defect is the no-texture region edge case (`region_enabled` set, `region_rect` left at zero, no later fill - confirmed by reading the whole of `importer.gd:_import`), which the existing `effect`-only coverage never reaches. The recommended fix is to **only enable the region when the rect can actually be computed**: move `region_enabled` / `region_filter_clip_enabled` and the rect assignment together inside the `if sprite_tex != null` branch, so a texture-less sprite ships as a plain (region-disabled) sprite instead of an invisible empty region, and delete the stale "filled in later" comment. This stays consistent with the mesh builder, which already leaves UVs raw when there is no texture (`mesh_builder.gd:79-85`). The one honest caveat: this is verified by static read of the import path; the with-texture region rect should still be confirmed by actually running the headless test once with a real-texture fixture, since no run was performed during this study. The two doc rows are pointers, not new prose: the `_001` suffix convention onto `docs/04-godot-plugin/index.md`, and a one-line multi-frame-preview caveat there pointing back at `packages/fixtures/README.md:135-136`.
