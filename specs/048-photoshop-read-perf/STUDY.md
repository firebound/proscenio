# Spec 048: Photoshop document-read performance

Two performance items for the UXP plugin: one cheap re-render fix that ships today, and one larger document-read rewrite that can only be proven against a real PSD in a live session.

## Scope

- **Scope the `busy` flag off the whole tag list** so a single rename does not re-render every `TagRow`.
- **Replace the synchronous DOM walk in `adaptDocument` with one `batchPlay` multiGet**, rebuilding the tree in JS - which turns the read asynchronous and ripples through every read path, built as a try-multiGet -> DOM-fallback fast path so a wrong descriptor degrades safely.
- Pull the sibling deferred item **shared adaptation per tick / lazy preview** into the same live session, since both can only be validated against a real PSD.

## Study

### Surface notes

**The busy flag is a per-row prop, and that - not the memo - is the bug.** `useTagTree` owns a single `busy` boolean (`hooks/useTagTree.ts:44`) that flips `true` for the whole duration of one rename and back to `false` in the `finally` (`hooks/useTagTree.ts:122-133`). That one boolean is threaded down unchanged: `ProscenioTagsPanel` passes `busy={tags.busy}` into `TagsSection` (`panels/ProscenioTagsPanel.tsx:69`), which fans it through `TagNodeList` -> `TagNodeBranch` -> every `TagRow` (`panels/sections/TagsSection.tsx:51,64,86,128`), and each `TagRow` spreads it onto `disabled={busy}` for the ignore/merge glyphs, the kind/blend selects, the advanced expander, and `TagDetails`' inputs (`panels/sections/tags/Row.tsx:147,154,162,173,187,196`; `panels/sections/tags/Details.tsx:107,117,128,137,145,149,159,171,176,179`). The earlier backlog wording ("`tagRowEqual` fails") was inaccurate: `tagRowEqual` already compares `busy` in both its fast path and its structural path (`panels/sections/tags/Row.tsx:211,220`), and it is *correct* to do so - a memo that ignored `busy` would leave rows un-disabled. The real cost is upstream: because `busy` is a single value shared by every row, one rename toggles it `false -> true -> false`, and on each flip `tagRowEqual` returns `false` for *every* row in the tree, so the whole list re-renders twice per rename. On a deep PSD that is the felt jank, and it is entirely separate from the IPC walk.

**Three ways to scope the disable, in increasing fidelity.** (1) *Drop the disable entirely.* Renames serialize through Photoshop inside `core.executeAsModal` (`api/layer-rename.ts:42`) and a second rename just queues another modal; the disable is defensive UI, not a correctness gate, so removing the `busy` prop and every `disabled={busy}` is the smallest diff and removes the re-render at the source. (2) *Track the in-flight `layerPath` instead of a boolean.* `useTagTree` would hold the path being renamed; only the row whose `node.layerPath` matches sees `disabled`, so a rename re-renders one row, not the tree. This keeps the affordance but changes the hook's public shape (`busy: boolean` -> something path-shaped) and means `tagRowEqual` compares a per-row derived flag. (3) *Push the disable through React context to the leaf controls only.* The controls that actually need disabling subscribe to a `BusyContext`; the row body stops carrying `busy` as a prop, so a `busy` flip no longer changes any `TagRowProps` and `tagRowEqual`'s fast path holds for the whole tree. Most surgical for the re-render but the most code. Option 1 is the recommended default unless a live session shows a real double-submit hazard; option 2 is the fallback if the affordance must stay.

**`adaptDocument` is a synchronous DOM walk, and every read path assumes that.** `adaptDocument` (`api/adapt-document.ts:22`) reads `doc.layers`, recurses through `adaptLayer` (`:88`), and reads `.name` / `.visible` / `.id` / `.bounds` / `doc.guides` off the live UXP wrappers - one synchronous IPC round trip per property per layer. It is already hardened for the null / non-iterable layer-collection class via `toLayerArray` (`:51`) and `safeAnchor` (`:61`), so the *correctness* work is done; what remains is *cost*. The walk has exactly two callers, both synchronous. `readActiveLayerTree` (`api/active-document.ts:24`) returns `adaptDocument(doc)` directly. `useTagTree`'s `syncOnce` (`hooks/useTagTree.ts:56-73`) calls it through `readTree` (`:140-144`) inside a synchronous effect (`:75-77`) and inside the poll interval (`:88-94`), comparing against the prior tree and bailing when nothing moved. A third consumer, `useActiveLayerPath` (`hooks/useActiveLayerPath.ts:34,44`), reads the selection chain through a *different* sync path (`api/ps-selection.ts`), not `adaptDocument`, but it shares the same `version` trigger - so any change to the read cadence has to keep it in step.

**Going async ripples through the sync effect, not just the function signature.** Making `adaptDocument` return a `Promise` forces `readActiveLayerTree` and `readTree` to become async, which means `syncOnce` can no longer run synchronously inside `React.useEffect` and compare-then-`setState` in one tick. The viable shape is an async effect that fires the multiGet, awaits it, and then runs the existing structural compare (`elementsEqual(treeRef.current, snap.tree)`, `hooks/useTagTree.ts:65-72`) before `setTree`, guarded against the classic stale-async hazards: a mounted/cancellation flag so a resolved walk from an old `version` does not clobber a newer tree, and the existing `lastSyncAtRef` de-dupe (`:60,92`) kept so the poll still skips a tick when an event-driven read already covered the interval. A Suspense boundary is the wrong tool here - the tree refreshes continuously on a poll and must *not* unmount the user's open dropdowns / expanded rows on every refresh (the whole reason `buildTagTreeReusing` preserves node refs, `:62-64`), and Suspense re-suspends on each new promise. So: a cancellation-guarded async effect plus `setState`, not suspension.

**The multiGet descriptor and its fallback contract.** The replacement is one `action.batchPlay` call that reads the document's layers in a single round trip - a multiGet over `[{ _ref: "layer", _name: "..." }]` style targets with `extendedReference` property keys (`name`, `visible`, `layerID`, `bounds`, plus the group/`layerSection` signal) and `count: -1` to sweep the whole stack - then rebuilds the `Layer[]` tree in JS from the flat descriptor array using the layer-group nesting indices, replacing the per-property IPC of the current walk. The codebase already has the batchPlay + `executeAsModal` precedent to copy (`api/ps-selection.ts:85-100`, addressing by `_id`; `api/layer-rename.ts:42`), and the read does *not* need a modal - it is read-only - so it can run as a plain `batchPlay` without the modal banner. The fallback contract: wrap the multiGet in a try; on a thrown descriptor error, a non-array / wrong-shape result, or a parse failure rebuilding the tree, fall back to the existing synchronous `adaptDocument` DOM walk and keep that as the always-correct path. The DOM walk stays in the tree as the safety net, not as dead code. Critically, the exact key names and the group-nesting field in the returned descriptor differ across UXP / PS builds and cannot be confirmed from the type stub (`types/uxp.d.ts:99` types `batchPlay` only as `(commands: unknown[]) => Promise<unknown>`); they can only be validated against a real PSD in a live Photoshop session.

**The sibling deferred item shares this exact session.** `deferred.md:29` ("shared adaptation per tick / lazy preview") proposes adapting the document *once* per `version` bump and feeding the tag-tree, the export preview (`useExportPreview`, refreshed alongside in `panels/ProscenioTagsPanel.tsx:38-42`), and the active-layer consumers from one snapshot - removing the redundant second walk per event. It is the same async-snapshot plumbing as the multiGet work, validated the same way (React-hook timing only a real panel can confirm), and `deferred.md:29` already says it "rode the same session" as the multiGet reader. Scheduling them together avoids reworking the read path twice.

### Research notes

- **batchPlay multiGet precedent in-repo.** The plugin already drives Photoshop through `action.batchPlay` inside `core.executeAsModal` for writes and selection (`api/ps-selection.ts:85-100`, `api/layer-rename.ts:42`, `api/legacy-migration.ts:57`), addressing layers by `_id` to disambiguate same-named siblings (`api/ps-selection.ts:76-79`). The multiGet read reuses the same descriptor vocabulary but as a read (no modal) - the new ground is the *property-key set* and the *group-nesting reconstruction*, not the API call itself.
- **Why the wrappers go stale.** `api/layer-rename.ts:1-7` documents that `doc.layers` wrappers go stale inside `executeAsModal` on this UXP build, which is exactly why a batchPlay descriptor (addressing by id / reference, not by holding a wrapper) is the robust read primitive. The same staleness is the reason the current DOM walk reads everything in one synchronous burst.
- **Recovering the prior IPC diagnosis.** `deferred.md:33` notes the full IPC perf diagnosis (root cause, community references, per-entry scope sketches) lived in a now-deleted photoshop-performance backlog file and must be recovered from git history if the multiGet work needs the references. Pull it before the live session so the descriptor experiments start from the prior findings rather than from scratch.

### Verdict summary

**1 now, 3 gate.** Only the busy-flag re-render scope is buildable and verifiable today: the bug is that a single shared `busy` boolean is a prop of every `TagRow`, so one rename re-renders the whole tree twice; the fix is to stop passing a per-row `busy` (drop the disable, since renames serialize through `executeAsModal`, or track the in-flight `layerPath`), and `tagRowEqual` is left alone because it already compares `busy` correctly. Everything on the document-read side - the multiGet reader, the cost measurement that justifies it, and the shared-adaptation / lazy-preview sibling - gates on a single scheduled live Photoshop session, because the multiGet descriptor (property keys, group-nesting field, `count: -1`) cannot be validated against anything but a real PSD; there is no headless harness for it. The recommendation is two efforts: (1) the busy-flag PR now, verified by a normal review; (2) one batched live session that measures the IPC cost first, then - if the cost justifies it - lands the multiGet reader behind a try -> DOM-walk fallback and the shared-per-tick snapshot together, since they share the same async read path and the same validation. The hardened synchronous `adaptDocument` walk stays the correct, shipping read path the entire time, and remains in the tree as the fallback even after the reader lands.
