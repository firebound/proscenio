# Spec 055: Re-import contract

What survives a re-import is a core promise the pipeline makes at two stages - the Photoshop manifest into Blender, and the Blender-authored `.proscenio` into Godot - and at both the written promise disagrees with the code. The Photoshop guide states a manifest re-import is not weight-preserving, while the importer reprojects painted weights from a surviving sidecar Custom Property. The Photoshop importer rebuilds the armature from scratch on every run, against a guide claim that rotation, parenting, and weights survive. The Godot `reimporter.gd` is an empty `RefCounted` whose header promises a diff/merge that never runs, while the only reimport path that exists overwrites the generated scene wholesale. This spec settles the contract at each stage, then aligns the code and the docs to it.

This spec is STUDY-first: each item is a "which side is the truth" call, and the measurement is already done below. The first decision was a measure-both-sides situation and the code was read line by line before framing it; the framing reports what the code actually does and which side is stale, rather than assuming. The TODO lists the candidate work per outcome; the rows finalize once the contract is locked.

## Scope

- Decide and document what survives a Photoshop manifest re-import (painted weights, armature, parenting), then make the code and the guide agree.
- Decide whether the Photoshop importer should keep rebuilding the root armature every run, or reuse the existing one.
- Decide whether to build the non-destructive Godot reimporter (diff/merge preserving user edits) or to drop the claim, delete the dead stub, and document the wrapper-scene instancing pattern as the supported path.

## Open decisions

### 1. Photoshop re-import weight contract (doc-vs-code)

**Code anchors:** `importers/photoshop/planes.py` (`_ensure_mesh` lines 264-295: an unchanged placement short-circuits and returns the mesh untouched; a changed placement rebuilds the quad and calls `reproject_stored_sidecar(obj)`; `_snapshot_before_rebuild` lines 298-318 captures live vertex-group weights into the sidecar when none is stored, so a native Auto Weights bind is not dropped); `core/bpy_helpers/skinning/automesh_hook.py` (`reproject_stored_sidecar` lines 224-250: reprojects the stored sidecar entries onto the rebuilt quad's UV anchors); `core/skinning/weight_reproject.py` (`reproject_entries` lines 23-59: barycentric blend over 3 nearest UV donors, nearest-neighbor fallback, only None when no donor within `max_distance`); `core/skinning/sidecar_schema.py` (the `proscenio_weight_sidecar` payload that survives the geometry wipe because it is an object-level Custom Property); `tests/operators/test_psd_reimport.py` (lines 79-90 assert an unchanged-bounds re-import keeps painted weights intact; lines 93-133 assert a changed-bounds re-import reprojects rather than wipes; lines 136-152 assert native weights with no sidecar are snapshotted and survive); `docs/00-guides/01-advanced/01-photoshop.md` (lines 42-43, the `[!WARNING]` "Re-import is not weight-preserving ... the painted weights on every plane it touches are lost").

**Question:** The guide says a manifest re-import loses painted weights; the code reprojects them from a surviving sidecar. Is the guide stale because the code now preserves, or did the code regress the deliberately-distinct weight matrix (automesh regen PRESERVES, PSD re-import LOSES, re-rig LOSES) and quietly start preserving where it should not? Measured both sides before framing.

**What the code actually does (measured):** the code preserves, in two tiers. An unchanged placement is treated as an art retouch and the mesh - including automesh densification and painted weights - is left fully intact (`_ensure_mesh` lines 282-283, `test_reimport_unchanged_bounds_keeps_painted_weights`). A changed placement rebuilds the quad, but the painted weights live in the object-level `proscenio_weight_sidecar` Custom Property which survives the geometry wipe, and `reproject_stored_sidecar` re-applies them onto the fresh UV anchors (`_ensure_mesh` lines 291-294, `test_reimport_changed_bounds_reprojects_weights_not_wiped`). A native bind that wrote no sidecar is snapshotted just before the wipe so it is not lost either (`_snapshot_before_rebuild`, `test_reimport_changed_bounds_preserves_native_weights_without_sidecar`). The guide's `[!WARNING]` describing total weight loss is therefore stale, not a description of current behavior. This is the same snapshot-by-UV-then-reproject mechanism automesh regen uses (`docs/02-blender-addon/06-weight-paint.md:17`), so the matrix line that actually changed is "PSD re-import": it now behaves like automesh regen, not like re-rig.

**Options:**
- **(A) Doc is stale - update it to the two-tier preserve contract, keep the code.** State that a same-bounds re-import keeps weights and density intact, and a changed-bounds re-import reprojects painted weights from the sidecar onto the new quad (a follow-up automesh regen then redistributes them across a denser mesh). Re-label the weight-operation matrix so PSD re-import reads PRESERVES (via reproject), distinct from re-rig which still loses. No code change; the tests already pin this behavior.
- **(B) Code regressed - restore the documented "loses weights" behavior.** Strip the reproject call and the snapshot from `_ensure_mesh`, returning PSD re-import to a plain wipe. This contradicts the tests, which would have to be inverted, and throws away a feature the sidecar work deliberately built; it only makes sense if the product wants PSD re-import to behave like re-rig on purpose.
- **(C) Keep the reproject but gate it behind a preference / operator flag.** A "Preserve weights on re-import" toggle mirroring the existing automesh "Preserve weights on regen" switch, defaulting on. Most flexible, but adds UI surface and a second code path to test for a behavior the round-trip already wants by default.

**Recommendation:** **(A) the doc is stale; update it and keep the code.** The code, the three tests, and the automesh-regen precedent all agree that the sidecar reproject is intentional and is the better default; the lone dissenter is the prose `[!WARNING]`. (B) would delete a working, tested feature to satisfy out-of-date docs and is the wrong direction. (C) is over-engineering a setting nobody asked for. The matrix nuance to write carefully: PSD re-import now PRESERVES through the same reproject path as automesh regen, while re-rig (a fresh bind that does not consult the sidecar) still LOSES - do not collapse the three into one. Size **S** (rewrite the `01-photoshop.md` re-import section and the matrix row; no code).

### 2. Photoshop importer armature: rebuild every run vs reuse

**Code anchors:** `importers/photoshop/__init__.py` (`import_manifest` lines 70-94: every call runs `build_root_armature(...)` at line 73 unconditionally, before the layer loop; the returned `armature_obj` is what each stamped mesh re-parents to); `importers/photoshop/armature.py` (`build_root_armature` lines 21-43: always `bpy.data.armatures.new` + `bpy.data.objects.new` + a fresh root bone, no lookup of an existing rig); `importers/photoshop/planes.py` (`_place_and_tag` lines 124-127 and `_parent_to_root` lines 476-485: a non-slot mesh is re-parented to `armature_obj` on every re-import; a slot-attached mesh is left on its slot Empty); `docs/00-guides/01-advanced/01-photoshop.md` (lines 35-40, "the object is reused, so object-level data survives: transform (rotation, position) and parenting").

**Question:** `import_manifest` calls `build_root_armature` on every run, so a re-import always creates a brand-new armature object. The mesh-reuse path then re-parents every non-slot mesh onto that new armature. Does this destroy the rotation / parenting / weights the guide says survive, and should the importer reuse the existing armature when its shape is unchanged?

**What the code actually does (measured):** `build_root_armature` has no reuse branch - it unconditionally creates a new armature and a new root bone (lines 31-39). On a second import this leaves the prior armature orphaned in the scene and re-parents every non-slot mesh to the fresh one (`_parent_to_root`). The per-mesh weights are object-level and survive (decision 1), and a slot-attached mesh keeps its slot parent (`_place_and_tag` line 124 guards on `is_slot_empty`). What does not survive cleanly is the armature object identity and any rig the user built on it: a second import yields a duplicate `<doc>.rig` object, and bones / constraints / pose authored on the first armature are stranded on the now-orphaned copy while the meshes follow the new empty one. The guide's blanket "parenting survives" is true for slot meshes and for the parent-type, but misleading about the armature object the meshes hang from.

**Options:**
- **(A) Reuse the existing armature when present, only build when absent.** Look up the armature by name (`_armature_name(manifest)`) or by an origin tag; if found, reuse it and skip `build_root_armature`. Preserves a rig the user grew on the first import across re-imports and stops orphan-armature accumulation. The risk is a stale armature whose bone set no longer matches the manifest, but today the manifest only ever drives a single `root` bone, so there is nothing to reconcile yet.
- **(B) Keep rebuilding, and correct the guide to say the armature is regenerated.** Cheapest and honest: document that re-import replaces the root armature and that rig work belongs after the art settles (mirroring the weight-iteration advice). Leaves the duplicate-armature and stranded-rig rough edge in place.
- **(C) Rebuild the armature but re-home the previous one's children and delete the orphan.** A middle path that avoids accumulation without committing to reuse semantics; more moving parts than (A) for the same end state, and it still discards any pose / constraint authored on the old armature.

**Recommendation:** **(A) reuse the existing armature when present.** It matches the spirit of the mesh-reuse path that already exists right beside it in `planes.py` (find-by-tag, reuse in place) and removes both the orphan accumulation and the stranded-rig surprise, while the single-`root`-bone reality keeps the reconciliation trivial for now. Pair it with the decision-1 doc fix so the guide's "parenting survives" becomes accurate for the armature too. If reuse proves to need bone reconciliation once multi-bone import lands, that is a later, larger call - flag it then rather than pre-building it. Size **M** (a reuse branch in `build_root_armature` or its caller, plus a regression test that a second `import_manifest` does not create a second armature object).

### 3. Godot non-destructive reimporter: build diff/merge vs document the wrapper-scene path

**Code anchors:** `apps/godot/addons/proscenio/reimporter.gd` (the whole file: an empty `RefCounted`, no methods, header promising "diff the existing imported scene against new `.proscenio` data, preserving user-added nodes ... Not implemented yet - see .ai/skills/godot-plugin-dev.md"); `apps/godot/addons/proscenio/importer.gd` (`_import` lines 63-109: the real reimport path, an `EditorImportPlugin` that rebuilds the full `Node2D` tree from scratch every run and `ResourceSaver.save`s over the existing `.scn` at lines 104-109); `apps/godot/addons/proscenio/plugin.gd` (does not reference `reimporter.gd` at all - the stub is dead, unreferenced code); `.ai/skills/godot-dev.md` (lines 64-80: the reimport contract already written down - reimport always overwrites, and the supported survival mechanism is wrapping the imported scene in your own `.tscn`, with the wrapper holding scripts, extra nodes, and its own `AnimationPlayer` / `AnimationLibrary`); `docs/04-godot-plugin/index.md` (lines 7-8: "Reimport to a native scene" plus "Wrapper-scene safety - a user-authored wrapper scene that instances the generated one survives every reimport").

**Question:** `reimporter.gd` promises a diff/merge that never runs; the actual `EditorImportPlugin` overwrites the generated `.scn` wholesale on every reimport. Is the non-destructive diff/merge worth building, or is the wrapper-scene instancing pattern the honest supported path? This is the heavy product-strategy call.

**What the code actually does (measured):** the `.proscenio` is the source asset and the `.scn` is a generated import artifact; Godot's `EditorImportPlugin` model regenerates that artifact from source on every reimport, and `importer.gd` does exactly that, packing a fresh tree and saving over the output (lines 99-109). There is no place for a user edit to live inside the generated `.scn` - the engine owns it. The `reimporter.gd` stub is never instantiated (`plugin.gd` has no reference to it) and its header points at `.ai/skills/godot-plugin-dev.md`, a file that does not exist (the real skill is `.ai/skills/godot-dev.md`). Meanwhile the wrapper-scene pattern - instance the generated scene into a user-owned `.tscn`, attach scripts and gameplay nodes to the wrapper, give the wrapper its own `AnimationPlayer` for Godot-authored animation - is already fully written in `godot-dev.md:64-80` and named as the safety guarantee in `docs/04-godot-plugin/index.md:8`. So the supported path already exists and is documented; the gap is the dead stub and its broken promise, not a missing user capability.

**Options:**
- **(A) Drop the diff/merge claim - delete the dead stub and document the wrapper-scene pattern as the supported path.** Remove `reimporter.gd` (it is unreferenced), and make sure the user-facing docs state plainly that reimport overwrites the generated scene and that the wrapper scene is how you keep edits. Most of this is already written in `godot-dev.md`; the work is deleting dead code, fixing the dangling skill reference, and confirming the guide is unambiguous. Honest and small; declines a capability the engine model makes awkward.
- **(B) Build the diff/merge reimporter for real.** A true non-destructive merge would have to load the prior `.scn`, classify each node as source-driven vs user-added, re-emit source-driven content, and graft user-added nodes / scripts / custom animations back on by stable identity across renames. This fights Godot's import model (the importer's job is to produce a generated artifact, not to merge into a prior one), needs a durable node-identity scheme to survive Blender-side renames, and is a large, ongoing-maintenance feature. Highest power, highest cost and risk.
- **(C) Keep the stub but make it explicit "not planned", or convert it to a documented no-op.** Cheapest paper fix: leave a marker that diff/merge is intentionally not done and point at the wrapper pattern. Leaves dead code in the tree and a half-promise that invites the same confusion later; strictly worse than (A) for the same intent.

**Recommendation:** **(A) drop the claim, delete the stub, lean on the wrapper-scene pattern** - but this is the product-strategy call to lock with the user, not to decide unilaterally. The evidence points hard at (A): the wrapper pattern is already the documented contract, already provides the user guarantee, and fits how `EditorImportPlugin` is meant to work, while the stub is dead code chasing a feature that fights the engine. (B) is defensible only if a concrete workflow genuinely needs edits to live inside the generated scene rather than in a wrapper, and no such workflow is on record. What would settle it: a user decision on whether "edits survive reimport" must mean inside the generated scene (then (B)) or is satisfied by the wrapper boundary (then (A)). Size **S** for (A) (delete `reimporter.gd`, fix the `godot-plugin-dev.md` dangling reference, tighten the guide wording); **L** for (B) (node-identity scheme + diff/merge engine + rename survival + tests).

## Verdict summary

**3 decisions. One is doc-only and code-confirmed; two carry code or product weight.** Decision 1 is measured and clear: the code preserves weights via the sidecar reproject (two tiers - intact on unchanged bounds, reprojected on changed bounds), the `[!WARNING]` is stale, and the fix is a doc rewrite plus a careful matrix relabel (PSD re-import now PRESERVES like automesh regen; re-rig still LOSES) - recommend (A), size S. Decision 2 is a real code rough edge: the importer builds a fresh armature every run, orphaning the old one and stranding any rig grown on it; recommend (A) reuse-when-present, size M, paired with the decision-1 doc fix so "parenting survives" becomes true. Decision 3 is the heavy product-strategy call: the diff/merge `reimporter.gd` is dead, unreferenced code promising a feature that fights Godot's import model, while the wrapper-scene pattern is already the documented, working contract - recommend (A) drop the claim and delete the stub (size S), but lock it with the user, because (B) build-it-for-real (size L) is only right if a workflow needs edits inside the generated scene.
