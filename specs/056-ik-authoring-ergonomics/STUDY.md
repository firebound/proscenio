# Spec 056: IK authoring ergonomics

The IK target wiring and the bake-at-export gate shipped (the `Rigging, drivers, IK` calls in [`decisions.md`](../decisions.md)), but the authoring surface around them is thin. The `Toggle IK` operator names a behavior it does not have, nothing in the addon shows that an IK chain exists, the constraint properties live only in Blender's native Bone Constraints menus, the `.IK` control bone leaks into the Godot export, and none of the Rigify-style visual affordances (named bone collections, theme colors, custom shapes) are used. This spec makes IK chains legible and editable from inside Proscenio, mirroring Rigify as the design precedent where it earns its weight.

This spec is STUDY-first for the four feature-shaped calls. Two calls are already locked from the 2026-06-11 manual session and are not re-litigated here: the pole bone is the default scaffolding (a second `.pole` control bone per chain, the cost of two control bones accepted), and the IK DOF locks (`lock_ik_*` + a rest pre-bend) ship as an opt-in panel option, never a default, because loose locks are hidden bone state that reads as "the bone will not rotate" with no explanation. Neither is built yet - the current `authoring_ik.py` creates only the single `.IK` target. The control-bone export leak (decision 4) is objective and can land first, independent of every design call below.

## Scope

- Rename `Toggle IK` so its create / remove behavior is honest, or evolve it into a real influence toggle. (`PROSCENIO_OT_toggle_ik_chain`, `panels/skeleton.py:248`.)
- Show that an IK chain exists: a Skeleton-panel marker on the constrained bone and on its control bone, plus an "IK chains" section listing each active chain (tip, chain length, target).
- Expose the constraint properties (chain length, influence, pole target) in the panel, with influence keyframable as the seed of an IK/FK blend, without simply re-drawing Blender's native constraint UI.
- Stop the `.IK` (and `.pole`) control bone leaking into the Godot export by filtering non-deform bones in the writer, both the skeleton and the animation paths.
- Apply Rigify-style affordances: a "Proscenio Controls" bone collection with a theme color and a custom shape, so control bones read as controls rather than deform bones.

## Open decisions

### 1. Rename or evolve `Toggle IK`

**Code anchors:** `apps/blender/operators/armature/authoring_ik.py` - `PROSCENIO_OT_toggle_ik_chain` (`bl_idname = "proscenio.toggle_ik_chain"`, `bl_label = "Proscenio: Toggle IK"`, lines 73-128); `execute` branches on `bone.constraints.get("Proscenio IK")` - present means remove the constraint and the suffix-matched control bone (lines 104-111), absent means create the control bone and a fresh `IK` constraint with `chain_count = self.chain_length` (lines 113-128). `panels/skeleton.py:248` draws it as `text="Toggle IK"`. The backlog entry "'Toggle IK' is a misleading name" is the source.

**Question:** The operator is not a state toggle. It creates or destroys the whole constraint plus its scaffolding bone, while the label "Toggle" promises switching something persistent on and off (influence on/off, an IK/FK blend). Is the lasting model a conditional create / remove label, or a real influence toggle that lives alongside a separate create action?

**Options:**
- **(A) Conditional create / remove label.** One operator, label resolved from the active bone's state in `draw` (or a dynamic `description`): `Add IK Chain` when no `Proscenio IK` constraint is present, `Remove IK Chain` when one is. Honest about the destructive create / destroy it already does; smallest change; the `Skeleton chrome` precedent (Quick Armature Esc shipped a dynamic header label rather than new behavior) shows the project prefers a label fix to a behavior change when the data path is already correct.
- **(B) Real influence on/off toggle, create stays separate.** Split into `Add IK Chain` / `Remove IK Chain` (the create / destroy path) plus a true toggle that flips `constraint.influence` between 0 and 1 (or `constraint.enabled`) on an existing chain. Matches the word "toggle" literally and seeds the IK/FK blend, but two operators where one stood, and an influence flip is better expressed as the keyframable slider in decision 3 than as a binary button.
- **(C) Leave the name, document it.** Cheapest, but the backlog logged this as confusing on first contact; the name actively mis-states the behavior, so this only defers the cost.

**Recommendation:** **(A) conditional create / remove label.** It removes the mismatch with the least surface, keeps one operator, and does not preempt the IK/FK blend - which decision 3 delivers properly as a keyframable influence slider rather than a binary toggle. The literal "toggle" semantics of (B) are real value but belong on the influence slider, not on the create/destroy button. Resolve the label in `draw` from the active bone's `Proscenio IK` presence (the same state `execute` already reads), and update `bl_label` / `bl_description` to match. Size **S**.

### 2. Surface that an IK chain exists

**Code anchors:** `apps/blender/panels/skeleton.py` - `PROSCENIO_UL_bones.draw_item` (lines 46-101) draws each bone flat with a `BONE_DATA` icon and connected / disconnected / relative flags, no IK awareness; the constrained bone and its `.IK` control sit in the same list undistinguished. `panels/_list.py:63` `draw_select_marker` (the per-row dot) and `_helpers.py:159` `draw_target_readout` are the existing row-cue and section-readout patterns to reuse. The chain data is on the constraint: `constraint.name == "Proscenio IK"`, `constraint.subtarget` (the control bone), `constraint.chain_count`; `_chain_member_bones` (`authoring_ik.py:131-147`) already walks the constrained bone toward the root by `chain_count`. The backlog entry "Zero indication of IK configured" is the source; today the only signal is the `.IK` suffix, which can be renamed.

**Question:** What marks an IK chain in the panel, and what does the "IK chains" section list? The constraint carries tip (the constrained bone), length (`chain_count`), target (`subtarget`); the marker has to read live state, not a name suffix, since the suffix can be renamed.

**Options:**
- **(A) Row marker only.** Add a `CON_KINEMATIC` icon to a `draw_item` row when the bone carries a `Proscenio IK` constraint, and a control-bone glyph when the bone is some chain's `subtarget`. Cheap, in place, but a flat list still hides the tip-to-target relationship.
- **(B) "IK chains" section only.** A new subpanel listing each `Proscenio IK` constraint once: tip bone, `chain_count`, control bone (`subtarget`), with a click that selects the tip. Reads as a chain inventory but leaves the bone list itself ambiguous.
- **(C) Both - row markers plus an "IK chains" section.** The marker answers "is this bone part of a chain" while scanning the hierarchy; the section answers "what chains exist and what do they target." This is the Rigify split (colored bones in the viewport plus the Rig Layers inventory panel). Largest of the three but each half does a job the other cannot.

**Recommendation:** **(C) both.** The backlog asked for both explicitly, and they are complementary, not redundant - the marker is the in-list cue, the section is the inventory. Drive both from a single scan over `armature.pose.bones` collecting bones whose `constraints` include a `Proscenio IK` (keyed by tip name, with `subtarget` and `chain_count`); reuse `draw_select_marker` for the row glyph and a `template`-free custom column (the pattern `Slots` attachments already use) for the section, with a select-the-tip operator. Do not invent stored chain state; the constraint is the single source so the panel cannot drift from the rig. Size **M**.

### 3. Constraint-property exposure depth

**Code anchors:** The IK constraint is a native `bpy.types.KinematicConstraint`: `chain_count` (static), `influence` (animatable - it is a keyframable RNA property), `pole_target` / `pole_subtarget` / `pole_angle` (static). The operator seeds `chain_count = self.chain_length` (`authoring_ik.py:120`) but exposes no post-creation edit. The locked pole-bone-default call means a `.pole` control bone is created alongside `.IK` (not yet built), so `pole_subtarget` will normally point at a Proscenio-owned bone. The locked DOF-lock call means a per-chain "lock chain in-plane" toggle (`lock_ik_x/y/z` + a rest pre-bend) is an opt-in panel option, not a default. `panels/skeleton.py:218-224` is the precedent for an in-panel property control next to a bone (`prop` + operator). The backlog entry "Constraint properties inaccessible via Proscenio" is the source.

**Question:** How much of the constraint surface belongs in the panel before it just mirrors Blender's native Bone Constraints UI? `chain_count` and the pole are static; `influence` is animatable and is the embryo of the IK/FK blend.

**Options:**
- **(A) Influence slider only.** Expose the one animatable, behavior-shaping property - `influence`, keyframable from the panel (a `prop` honors keying; add an explicit insert-keyframe affordance for the IK/FK blend seed). Smallest, highest-value; chain length and pole stay in the native UI. Leaves a re-run of decision 1's operator as the only way to change chain length.
- **(B) Curated trio: chain length, influence (keyframable), pole target.** The exact set the backlog named. `chain_count` as an editable `IntProperty`-style `prop` on the constraint, `influence` keyframable, `pole_target` / `pole_subtarget` surfaced (defaulting to the Proscenio `.pole` bone). Plus the opt-in "lock chain in-plane" toggle from the locked DOF-lock call, which gives those hidden `lock_ik_*` flags a visible owner. Concentrates the IK flow in Proscenio as the addon intends, without redrawing stretch / weight / iterations / use_tail and the rest of the native panel.
- **(C) Full constraint mirror.** Re-draw the native `KinematicConstraint` UI inside Proscenio. Most complete, but it duplicates Blender's own panel with no added value and grows the maintenance surface for every native field - exactly the "before it just mirrors Blender's" line the question warns against.

**Recommendation:** **(B) curated trio plus the opt-in in-plane lock.** It matches the backlog's named set, concentrates the flow as the addon intends, and respects both locked calls - the pole target row is where the default `.pole` bone becomes visible and editable, and the "lock chain in-plane" toggle is where the otherwise-hidden `lock_ik_*` state gains a panel owner (the anti-pattern the DOF-lock call was guarding against). Stop short of stretch / iterations / weight: those are native-UI territory and not behavior the Proscenio export consumes (export bakes the chain, per the `Rigging, drivers, IK` call). Keep influence keyframable as the IK/FK-blend seed; do not over-build the blend itself here. Size **M**.

### 4. Export-leak filter rule

**Code anchors:** `apps/blender/exporters/godot/writer/skeleton.py` - `build_skeleton` (lines 93-139) iterates `iter_bones(armature)` at line 107 with no `use_deform` filter, so the `.IK` control bone is emitted as a `Bone2D`; `compute_bone_world_godot` (lines 69-90) iterates the same way and feeds `world_godot`. The animation path keys off the same bone set: `build_animations` -> `build_bone_track` (`exporters/godot/writer/animations.py:89-129`) emits a track per animated bone, and the writer builds `rest_local` only for the bones `build_skeleton` walks. `iter_bones` is the unfiltered helper (`core/bpy_helpers/_shared/_bpy_compat.py:46-48`). The fix has a direct in-repo precedent: skinning already filters `[b.name for b in armature.data.bones if b.use_deform]` (`core/bpy_helpers/skinning/automesh_hook.py:177`, `operators/skinning/bind_mesh.py:182`). The operator already sets `edit_bone.use_deform = False` on the control bone (`authoring_ik.py:56`), pinned by `tests/operators/test_toggle_ik.py:58`. The backlog entry "Control bone `.IK` leaks to export" is the source. This call is objective and lands first regardless of decisions 1-3.

**Question:** Adopt `use_deform=False` means "not exported" as the general writer convention, or narrowly filter the `.IK` suffix?

**Options:**
- **(A) General `use_deform=False` filter.** Skip non-deform bones in both `compute_bone_world_godot`/`build_skeleton` and (by consequence, since they only project bones the skeleton built) the animation tracks. This is the natural convention - a non-deforming bone is authoring scaffolding by definition, the export is a deform skeleton for `Polygon2D` skinning, and skinning already reads `use_deform`. It opens a clean path for a future controls layer (anything in "Proscenio Controls" is non-deform and stays out by the same rule), and it is suffix-agnostic so the `.pole` bone from the locked pole-default call is excluded for free, as is any hand-authored control bone.
- **(B) Suffix-only `.IK` / `.pole` filter.** Drop only bones whose name ends `.IK` (and `.pole`). Narrowest behavior change, but it couples the export to a name that can be renamed (the very weakness the backlog flagged about the suffix as a signal), misses hand-authored non-deform controls, and needs extending for every new control suffix.

**Recommendation:** **(A) general `use_deform=False` filter.** It is the convention the rest of the addon already follows for skinning, it is robust to renames, and it subsumes both `.IK` and `.pole` without enumerating suffixes. Apply it at the bone iteration in `compute_bone_world_godot` and `build_skeleton` so a control bone never enters `world_godot` or `rest_local`; the animation builder then drops its tracks for free, since it only emits for bones the skeleton carries a rest for (a stray control-bone fcurve resolves through `_REST_FALLBACK` today, so add the deform check in `collect_bone_keys` / `build_animation` as the belt-and-braces guard and assert it in the headless test). Headless test: a rig with `.IK` (and, once built, `.pole`) controls exports only the deform bones - the controls are absent from the skeleton `bones[]` and from every animation track. This is the one row that goes to [TODO.md](TODO.md) immediately. Size **S**.

### 5. Rigify-style affordances

**Code anchors:** A repo-wide grep for `bone_collections` / `color_set` / `custom_shape` on the addon returns no authoring writes - the only `bone_collections` use is a skinning visibility snapshot (`core/bpy_helpers/skinning/modal_session.py:30`, save / restore for the weight-paint modal), and there is no `color_set` or `custom_shape` write anywhere. So this is greenfield: the control bone created by `authoring_ik.py:43-58` gets no collection, color, or shape today. The relevant Blender APIs are `armature.collections.new("Proscenio Controls")` + `collection.assign(bone)`, `pose_bone.color.palette` (a theme enum like `THEME01`) or `bone.color.palette`, and `pose_bone.custom_shape` (a mesh object). The backlog entry "Rigify-style rig management" is the source; Rigify is the precedent (named colored collections, custom-shaped controls, color sets red-right / blue-left).

**Question:** How much of the Rigify affordance set is the cheap minimum worth shipping, given none of it exists yet?

**Options:**
- **(A) Bone collection only.** Create / reuse a "Proscenio Controls" collection and assign every control bone (`.IK`, `.pole`) to it on creation. Cheapest; gives a visibility toggle and a logical group, but the bones still look like deform bones in the viewport.
- **(B) Collection plus theme color.** Add a `color.palette` theme assignment so controls tint distinctly. Still cheap (an enum set), and color is the fastest viewport read of "this is a control" - it is the affordance an artist notices first.
- **(C) Collection plus theme color plus custom shape.** Add a generated control widget (a small ring / square mesh) as `custom_shape`, the full Rigify read. Highest polish; the custom shape is the costliest part - it needs a widget mesh created and managed (generated once into a hidden collection, Rigify-style), and a shape that scales sanely across bone sizes.
- **(D) None - defer entirely.** The `ik-chain-helper` capability is gated; argue the affordances ride with it. But the affordances are authoring legibility for the shipped toggle, not the gated one-click scaffolding, so deferring leaves the control bone visually indistinguishable from deform bones, which is the backlog's complaint.

**Recommendation:** **(B) collection plus theme color** as this spec's cut, with **(C)'s custom shape** noted as the natural follow-on. The collection gives grouping and a visibility toggle; the theme color is the cheapest high-value viewport cue and the one an artist reads first. The custom shape is real Rigify parity but carries widget-mesh creation and lifecycle management (generate once, hide, scale per bone), which is disproportionate for the first cut - split it out so it does not block the collection + color win. Create / reuse "Proscenio Controls" and set the palette when the control bone is made in `_create_target_bone`, extended to cover the `.pole` bone once the locked pole-default lands. Size **M** for (B); add **M** again if the custom shape (C) is pulled in.

## Verdict summary

**5 decisions; 1 ready to code now.** Decision 4 (the export-leak fix) is objective - take option (A), the general `use_deform=False` filter, and land it first as the one row that goes straight to [TODO.md](TODO.md), independent of the rest. The four feature-shaped calls await their pick: rename `Toggle IK` via the conditional create / remove label (1A, S); surface chains with both row markers and an "IK chains" section (2C, M); expose the curated trio chain length / keyframable influence / pole target plus the opt-in in-plane lock (3B, M); and ship the "Proscenio Controls" collection plus theme color now with the custom shape deferred (5B, M). All five build on the two locked 2026-06-11 calls - pole bone as the default scaffolding, DOF locks as an opt-in option not a default - and reference Rigify as the precedent for the legibility and affordance work. Once each call is locked it moves to [`decisions.md`](../decisions.md) and the implementable rows become [TODO.md](TODO.md). The gated `ik-chain-helper` and `ik-round-trip` capabilities stay out of scope.
