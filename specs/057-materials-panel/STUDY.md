# Spec 057: Materials panel

A user inspecting or configuring materials today hunts through the Shader Editor or Properties > Material per object: there is no Proscenio surface for cross-material inspection or bulk configuration. The reopened backlog item proposes a full inspection-and-configuration panel; spec 036 assessed that panel and dropped it, on the grounds that bulk image-path repair duplicates Blender's native `File > External Data > Find Missing Files` and the rest is speculative surface. The item came back by request, so this STUDY must answer that drop rationale before recommending a build, and it must separate the genuinely painful part (pixel art renders blurry) from the speculative part (a cross-material report and bulk config UI no logged workflow asks for).

This spec is STUDY-first. The reopened item bundles two questions that need different answers: the *scope* call (full panel versus a low-effort pixel-art shortcut) and a *quasi-bug* in the importer's material setup that is worth fixing on its own terms regardless of which surface wins. Reading the importer closed one premise in the backlog text: the pixel-art pain is not the blend mode (the importer never sets `HASHED`; it routes every mode to `BLEND`), it is the texture-node interpolation, which the import path leaves at Blender's blurry `Linear` default while the fixtures hand-set `Closest`. Decision 2 reframes the backlog's `HASHED`-versus-`CLIP` line accordingly.

## Scope

- Decide the surface: a full inspection-and-configuration panel, or the low-effort alternative (a `Pixel art` checkbox on the active element that sets `Closest` interpolation on its material's image-texture node).
- If the full panel wins: a material inspection list (name, users, image-texture nodes, filepath); cross-material quick config (interpolation, blend mode, extension, alpha mode, alpha threshold, mipmaps / anisotropic) applicable to all / selection / regex; bulk image-path repair; a material report (unique, image-sharing, isolated).
- Regardless of surface, resolve the importer's pixel-art default: the texture-node interpolation is unset (Blender default `Linear`), so imported pixel art is bilinear-blurred until the user fixes every material by hand.
- Out of scope: the Godot-side `texture_filter` (no schema field exists for it today and there is no per-element authoring of it); atlas-config items (`per-asset-ppu`, `per-object-pack-state`) stay in [`gated.md`](../gated.md).

## Open decisions

### 1. Full materials panel versus the low-effort pixel-art shortcut

**Code anchors:** `apps/blender/panels/_draw_sprite.py:19-29` (the Active Sprite body draw - where a `Pixel art` checkbox would surface; already walks `iter_material_images` for its readout at lines 13-15, 58-64); `apps/blender/panels/element.py:122-145` (the `PROSCENIO_PT_active_sprite` subpanel host, and the parallel `PROSCENIO_PT_active_mesh` at 98-119 for the mesh case); `apps/blender/core/_shared/material_images.py:30-85` (the canonical material node-tree walk - `iter_material_node_images`, `iter_material_images`, `first_material_image`, the building blocks any inspection list would reuse); `apps/blender/properties/object_props.py:79-201` (the per-Object `ProscenioObjectProps` group - where an `active`-element pixel-art toggle would live, alongside the existing `material_isolated` flag at 180-190).

**Question:** The backlog proposes a full panel: an inspection list (name, users, image-texture nodes, filepath), cross-material quick config across all / selection / regex, bulk image-path repair, and a material report (unique, image-sharing, `material_isolated=True`). Spec 036 dropped exactly this, reasoning that path-repair duplicates the native `Find Missing Files` and the rest is speculative. Does a real cutout workflow need the full surface, or do the pixel-art shortcut plus the existing native tools cover it?

Answering the drop rationale piece by piece: (a) Bulk image-path repair is a re-skin of `File > External Data > Find Missing Files` / `Report Missing Files`, which already recurses a chosen directory and rebinds by filename - the repository's import path also reloads images by path on every re-import (`planes._attach_material` at `planes.py:406` uses `bpy.data.images.load(..., check_existing=True)`), so a broken path is normally re-resolved by re-importing from the manifest, not hand-repaired. (b) The inspection list (name / users / image / filepath) restates what the Shader Editor and the Outliner's Blender-File view already show, with no Proscenio-specific derivation on top. (c) The material report (unique / image-sharing / isolated) is a read-only diagnostic with no logged demand; `material_isolated` already has a per-object home and a clear meaning (`object_props.py:180-190`). (d) The one item with a concrete, reproducible pain is interpolation for pixel art, and that is a single boolean on one node, not a cross-material matrix.

**Options:**
- **(A) Full inspection-and-configuration panel.** Implements the whole backlog list. Maximum surface and the largest new GUI-test burden in the addon (a `UIList` over `bpy.data.materials`, a regex/selection scope selector, a multi-field config block, a file-picker repair operator, a report block). Duplicates native tools (Find Missing Files, Shader Editor) for the parts with no demand signal, against the repository's "build on demand, do not add speculative surface" philosophy ([`gated.md`](../gated.md), [`dropped.md`](../dropped.md)). Hard to keep stable while the panels still churn.
- **(B) Low-effort `Pixel art` checkbox on the active element.** One `BoolProperty` on `ProscenioObjectProps` plus an `update` callback that walks the active object's materials via `iter_material_images`'s sibling node walk and sets each image-texture node's `interpolation` to `Closest` (and back to `Linear` when unchecked). Surfaces in `_draw_sprite.draw_body` (and the mesh body for parity, since a Polygon2D shows the same blur). Solves the one real pain, adds the minimum surface, leaves inspection and repair to the native tools the drop rationale already credited. The default-fix in Decision 2 means most users never need to touch it.
- **(C) Do nothing beyond Decision 2.** If the importer default is fixed for everyone (Decision 2 option A), freshly imported art is crisp with no UI at all. A checkbox is then only an after-the-fact override for a material a user blurred deliberately, or for a hand-authored mesh that never went through the importer. Smallest surface; the gap is the no-importer case (`Incorporate as Element` meshes from spec 050, `element.py:84-92`) where no import default ever ran.

**Recommendation:** **(B), scoped to interpolation only, and contingent on Decision 2.** It answers the spec-036 drop directly: the panel is mostly speculative (inspection restates native editors, repair duplicates Find Missing Files, the report has no consumer), so the full surface stays dropped; the one non-speculative item is pixel-art crispness, which (B) delivers as a single per-element toggle reusing the existing `material_images` walk and the existing Active-element subpanels. Keep it a per-element checkbox, not a `bpy.data.materials` panel, so it follows the active-object pattern the rest of the addon uses and carries no list/scope/report machinery. Do not build the regex/selection cross-material config, the inspection list, or the repair operator; if a real session later logs a multi-material batch-config need, reopen that slice with the logged case as its trigger (the [`gated.md`](../gated.md) pattern). Size **S** for the checkbox on top of Decision 2.

### 2. The importer's pixel-art default: texture interpolation, not blend mode

**Code anchors:** `apps/blender/importers/photoshop/planes.py:438-441` (the `ShaderNodeTexImage` node: `tex.image = image` is set, `tex.interpolation` is never touched, so it stays Blender's default `Linear`); `apps/blender/importers/photoshop/planes.py:65-77` (`_BLEND_METHOD_BY_MODE` - every entry maps to `"BLEND"`); `apps/blender/importers/photoshop/planes.py:457-473` (`_set_material_blend_method` - the fallback is `"BLEND"`, and `"HASHED"` appears only in the `Literal[...]` cast at line 471, never as an assigned value); `packages/fixtures/blink_eyes/build_blend.py:128`, `packages/fixtures/mouth_drive/build_blend.py:177`, `packages/fixtures/slot_swap/build_blend.py:166` (each fixture sets `tex.interpolation = "Closest"  # pixel-art: nearest-neighbor, no bilinear blur` - the fixtures bake the setting the real importer drops); `apps/blender/exporters/godot/writer/sprites.py:288-301` (`_per_sprite_texture` emits the texture filename but no filter; the Godot writer has no `texture_filter` field anywhere).

**Question:** The backlog frames this as "the importer sets `HASHED` by default, which dithers semi-transparent pixels, and pixel art wants `CLIP`." Reading the code, that premise is wrong: the importer never sets `HASHED` - `_set_material_blend_method` resolves every manifest mode through `_BLEND_METHOD_BY_MODE` to `"BLEND"`, so there is no dither-stipple bug from the blend method. The actual, reproducible pixel-art defect is one level over: `_attach_material` builds the image-texture node and binds the image but never sets `tex.interpolation`, so it stays `Linear` (bilinear), and every imported sprite is blurred under magnification until the user fixes it by hand. The fixtures already work around this with an explicit `Closest`. So the question is not `HASHED` versus `CLIP`; it is: should the importer set `Closest` interpolation for everyone, or leave it for the chosen surface to control?

**Options:**
- **(A) Fix the importer default for everyone: set `tex.interpolation = "Closest"` in `_attach_material`.** One line next to `tex.image = image` (`planes.py:441`), guarded the same defensive way as the colorspace and blend-method assignments nearby (the attribute exists on `ShaderNodeTexImage` across supported Blender versions, so a plain set is safe, but a `getattr`-guarded set matches the file's style). Makes the import path match what every fixture already does, so the viewport shows crisp pixel art with zero user action. Pixel art is the product's stated target (the fixtures' own comments call it out), so `Closest` is the right default, not an opinionated override. Risk: a user importing smooth/painted (non-pixel) art would now get nearest-neighbor and may want `Linear` back - which is exactly what the Decision 1 checkbox provides as the escape hatch. Size **S**.
- **(B) Leave the importer at `Linear`; make the Decision 1 checkbox the only control.** No import-path change; the user ticks `Pixel art` per element to get `Closest`. Keeps the importer opinion-free, but every pixel-art import starts blurry and the user must visit each element - the friction the fixtures avoided by baking `Closest`. Pushes a default-quality problem onto a manual step. Size **S** (no new code beyond Decision 1).
- **(C) Scene-level "default interpolation" preference applied on import.** A `scene_props` enum (`Closest` / `Linear`) read by `_attach_material`, plus the per-element override from Decision 1. Most flexible; but it is a new preference for a default that pixel art almost always wants the same way, and it adds a second place interpolation is decided. Speculative against one obvious default. Size **M**.

**Recommendation:** **(A), with the Decision 1 (B) checkbox as the per-element override.** This is a quasi-bug, not a setting: the importer already commits to flat unlit pixel-art materials (the unlit Emission/alpha shader at `planes.py:434-449`, the explicit sRGB decode at `planes.py:408-418`) and every fixture hand-sets `Closest`, so leaving the live import path on `Linear` is an oversight that ships blurry art by default. Fix it for everyone in `_attach_material` (one guarded line), and let the Decision 1 checkbox flip an individual element back to `Linear` for the rare smooth-art case. Correct the backlog text from "`HASHED` to `CLIP`" to "unset interpolation (`Linear`) to `Closest`" so the record matches the code; the blend mode is already `BLEND` and needs no change. Leave the Godot `texture_filter` out of scope: there is no schema field for it, the writer emits none (`sprites.py:288-301`), and per-project import settings are the engine-side norm - reopen only if a logged import shows Godot re-blurring crisp source art. Size **S** (option A) plus **S** (the Decision 1 checkbox) = **S** overall.

## Verdict summary

**2 decisions, both ready once the calls are locked; combined size S.** Decision 1: keep spec 036's drop of the full materials panel (inspection restates native editors, bulk repair duplicates Find Missing Files, the report has no consumer) and ship only the non-speculative slice - a per-element `Pixel art` checkbox (option B) reusing the existing `material_images` walk and Active-element subpanels - and only if Decision 2's default leaves a real override case. Decision 2: the backlog's `HASHED`-versus-`CLIP` framing is wrong against the code (every mode already maps to `BLEND`); the real defect is the unset texture-node interpolation that ships blurry pixel art, so fix `_attach_material` to set `Closest` for everyone (option A), with the Decision 1 checkbox as the per-element escape hatch. The two are coupled: with the importer default fixed, the checkbox is a small override, so build Decision 2 first and let it size the checkbox. The Godot `texture_filter` stays out of scope (no schema field, no writer emission, engine-side default is the norm). Once locked, the call moves to [`decisions.md`](../decisions.md) and the implementable rows become [TODO.md](TODO.md).
