# Spec 058: Quick Armature interaction redesign

The Quick Armature modal binds Shift, Alt, Ctrl, X, and Z all at once, conflating chain modifiers (Shift / Alt select the parenting category) with standalone tools (Ctrl grid snap, Ctrl+Z undo, X / Z axis lock). The taps read as arbitrary because nothing groups them, and the scheme is saturated - there is no free modifier left for viewport pick-parent (hit-test a bone tip to reparent mid-sketch), which has confirmed demand. This spec redesigns the interaction vocabulary first, then fits pick-parent into the new scheme.

This spec is STUDY-first and was returned from [spec 050](../050-blender-authoring-design/STUDY.md) for exactly this reason: spec 050 analyzed this item as its decision #2 (`qa-quickarm-interaction-revision`) and leaned mode-layer, but flagged it as the heaviest of the five and not ready to code. This file expands that single decision into the full decision set a dedicated spec needs. **It pauses here for the calls: the TODO finalizes once the scheme is locked.** Each decision below carries its code anchors, concrete options, a recommendation, and the locked promise it must respect. Build on the spec-050 lean - do not contradict the mode-layer direction without a stated reason.

How to use this file: read each decision, pick an option (or amend), and record the call. The chosen calls then move to [`decisions.md`](../decisions.md) under "Quick Armature UX" and the implementable rows become [TODO.md](TODO.md).

## Scope

- Replace the saturated modifier-tap chord scheme with a vocabulary that separates chain modifiers from standalone tools.
- Add viewport pick-parent (hit-test a bone tip to reparent mid-sketch) as a first-class part of the new scheme. This absorbs the former `qa-pick-parent-viewport` item.
- Keep every locked Quick Armature UX promise intact.

## The saturated scheme today

The modal binds nearly every reachable key, and the bindings split across two unrelated jobs.

**Code anchors:** `operators/armature/quick_armature.py` routes raw events in `modal` (`quick_armature.py:231`) through a fixed precedence: exit / confirm (`_is_exit_event` at `:832`, `_is_confirm_event` at `:836`), then `_is_undo_event` / `_is_redo_event` (`:840`, `:844` - Ctrl+Z and Ctrl+Shift+Z), then `_is_axis_lock_event` (`:848` - bare X / Z), then in-canvas MOUSEMOVE / LEFTMOUSE. Ctrl is tracked on every event for grid snap (`cls._ctrl_held = bool(event.ctrl)` at `:242`, consumed in `_post_process_world_point` at `:310`). The parenting category is read off Shift / Alt at PRESS time in `_handle_leftmouse` (`:378`-`:384`) via `resolve_press_mode_label`, and committed at RELEASE via `resolve_press_mode` (`:409`). The chord math is pure in `core/armature/quick_armature_math.py`: `resolve_press_mode_label` (`quick_armature_math.py:25`) maps `(shift, alt, default_chain)` to one of `connected` / `unparented` / `disconnected`, and `resolve_press_mode` (`:51`) turns that label into `(parent_to_last, connect)`. The rendered cheatsheet is `operators/armature/_status_bar.py:emit_chord_layout` (`_status_bar.py:23`), a fixed seven-row list built on the shared `chord` primitive (`operators/_status_bar.py:19`).

**The conflation, concretely:**

- **Chain modifiers** (which parenting the next bone gets): Shift flips connected vs unparented per `default_chain`; Alt forces disconnected (parent set, head free). Held during the LMB drag.
- **Standalone tools** (state that persists across drags): Ctrl = grid snap while held; X / Z = a sticky axis-lock toggle (`_toggle_axis_lock` at `:264`); Ctrl+Z / Ctrl+Shift+Z = the in-modal undo / redo stack (`_undo_last_bone` at `:589`, `_redo_last_bone` at `:616`).

Every modifier is spent, and the two jobs share the same keys with no visual or mental grouping. `_is_axis_lock_event` already has to special-case the overlap (it requires no Ctrl / Shift / Alt so it does not steal Ctrl+Z or collide with the Shift chain - see the comment at `:849`-`:854`). That carve-out is the saturation made visible in code: a new gesture (pick-parent) has nowhere to land without another carve-out.

## Open decisions

### 1. The replacement interaction vocabulary

**Code anchors:** the saturated scheme above (`quick_armature.py:231`-`:262` dispatch, `_status_bar.py:23` cheatsheet, `quick_armature_math.py:25`-`:71` chord math). The closest in-repo precedent for the alternative is the automesh authoring modal: `operators/automesh/automesh_authoring.py` runs a multi-stage modal where a per-instance `_stage` is mirrored to a ClassVar `_current_stage` (`automesh_authoring.py:313`-`:314`), the status bar reads that ClassVar to draw the active stage's chords (`_draw_statusbar_authoring` at `:1305`-`:1311`, which calls `emit_authoring_chord_layout` with the stage), and events route through a per-stage dispatcher (`_handle_stage_event` -> `_pen_event` / `_neutral_event` at `:459`-`:484`). Locked: `decisions.md` "Quick Armature UX" (GPU preview line + real bone on click, tail tracks MOUSEMOVE; prefix = preference + F3; Front-Ortho auto-snap restores prior view on exit).

**Question:** Shift / Alt / Ctrl / X / Z are all bound and conflate chain modifiers with standalone tools, and viewport pick-parent has no free key. What vocabulary replaces the taps, before fitting pick-parent in?

**Options:**
- **(A) Mode-layer scheme.** A key (Tab is the natural pick - Blender's own mode toggle, and currently unbound in the modal) cycles a modal sub-mode. The default mode is **Draw** (the current click-drag bone authoring, chain category still on Shift / Alt within that mode). A second mode is **Reparent** (LMB hit-tests a bone tip to reparent; see decision 2). The status bar swaps to show only the active mode's chords - exactly the `automesh_authoring.py` pattern (`:313`, `:1305`). Standalone tools that are genuinely global (grid snap, undo / redo, axis lock) can stay on their current keys, or relocate, but they no longer have to share the chain modifiers' keys because the mode disambiguates intent. Frees the saturation, adds one mental step (which mode am I in), reuses an existing in-repo architecture, and preserves every locked promise (Draw mode is the current behavior unchanged).
- **(B) Alt+click as a direct parent-pick.** Overload Alt: Alt+LMB near a bone tip picks that bone as the parent for the next drag, falling back to disconnected when no tip is hit. Minimal surface (no new mode, no status-bar swap), but Alt already means disconnected (`resolve_press_mode_label` at `quick_armature_math.py:44`), so the same chord would mean two things distinguished only by whether the cursor happens to be near a tip - ambiguous and unteachable. It also does not relieve the saturation; it deepens it.
- **(C) Standalone Reparent operator outside the modal.** A separate `proscenio.reparent_bone` operator (mirroring `rotation_mode.py`'s shape - active-bone / armature scope, `bl_options REGISTER, UNDO`, picker-first armature resolution at `rotation_mode.py:21`). Leaves the modal chords untouched, but breaks the one-session authoring flow the whole modal exists to provide: the user would exit the modal, run the operator, re-enter. The backlog item explicitly wants pick-parent *mid-sketch*.

**Recommendation:** **(A) mode-layer.** It is the only option that both relieves the saturation and gives pick-parent a teachable home, it preserves every locked promise because Draw mode is the current behavior verbatim, and it reuses the `automesh_authoring.py` mode-dispatch + status-bar-swap architecture rather than inventing one - so the cost is wiring, not design risk. This confirms the spec-050 lean with the added grounding that an in-repo precedent already implements the hard parts (per-mode handler routing, ClassVar-driven status-bar repaint, pixel-radius hit-testing). The chain-modifier semantics (Shift / Alt within Draw) and the standalone tools (Ctrl snap, Ctrl+Z, X / Z) stay as they are within Draw mode; the redesign's deliverable is the mode layer plus the Reparent mode, not a re-lettering of the existing Draw chords. Size **M** (a `_mode` ClassVar + a Tab handler before the LEFTMOUSE branch in `modal` at `:260`, a per-mode LEFTMOUSE dispatch, a mode-aware `emit_chord_layout`, and a `tag_redraw` of VIEW_3D + STATUSBAR on mode switch mirroring `_tag_redraw_view3d` at `automesh_authoring.py:1315`).

### 2. Where pick-parent sits, and how it resolves the hit-test

**Code anchors:** `core/bpy_helpers/_shared/viewport_math.py:region_event_to_xz_offset` (`viewport_math.py:126`) projects an offset pixel position onto the Y=0 XZ plane, returning `None` on a parallel view or a behind-camera hit - the automesh modal already uses it for a pixel-radius pick (`automesh_authoring.py:408`, `near_world = region_event_to_xz_offset(context, event, dx=self._STROKE_PICK_RADIUS_PX)`). `core/_shared/nearest.py:nearest_index` (`nearest.py:20`) is the pure, dimension-agnostic "closest candidate within an optional max distance, returns -1 past the cap" scan used by the contour splice, the stroke snap, and the weight transfer. The bone tips to test against are `armature.data.bones[*].tail_local` mapped to world via `armature.matrix_world` (the exact pattern already in `_effective_drag_head` at `quick_armature.py:452` and `_resolve_parent_tail_world` at `_overlay.py:107`). The parent state today is the single `cls._last_bone_name` (`quick_armature.py:110`); reparent makes that user-chosen instead of always-the-last.

**Question:** In the mode-layer scheme, pick-parent is the Reparent mode. What does a click in that mode do, and how does it resolve which tip was hit (including when no tip is under the cursor)?

**Options for the hit-test resolution:**

- **(A) Nearest tip within a pixel radius, world-space project then `nearest_index`.** On LMB in Reparent mode, project the cursor to the XZ plane with `region_event_to_xz_offset` (`viewport_math.py:126`), build the world-space tail list from `bones[*].tail_local @ matrix_world`, and call `nearest_index(cursor_xz, tails, max_distance=R)` (`nearest.py:20`) with a world R derived from a fixed pixel radius (the automesh `_STROKE_PICK_RADIUS_PX` approach at `:408`, so the pick tolerance is screen-constant across zoom). The hit bone becomes `cls._last_bone_name`; the next Draw-mode drag chains from it. Reuses two existing primitives, screen-stable, and is headless-testable because the math is the pure `nearest_index`.
- **(B) Nearest of tip-or-head.** Same scan but over heads and tails both, so the user can reparent onto a root's head. More forgiving but muddier - "parent" in this modal means "chain from the previous tail" (`_create_bone` snaps the child head to the parent tail at `:554`), so head hits have no natural chaining semantics. Adds ambiguity for a case the connected-chain model does not express.
- **(C) Blender's native bone ray-pick** (`view3d_utils` region-to-ray plus `bpy.ops`-style selection). Most accurate in 3D, but the whole modal is a flat Y=0 picture-plane tool (`mouse_event_to_plane_point(..., plane_axis="Y")` everywhere), so a planar nearest-tip scan matches the mental model and avoids dragging a 3D picker into a 2D workflow.

**Fallback when no tip is hit (within the radius):**

- Resolve to **no reparent**: keep the current `cls._last_bone_name`, report "no bone tip near cursor", and stay in Reparent mode (the user missed; let them click again). This mirrors the "lenient miss" the modal already shows for a stray click that is too short (`bone too short, skipped` at `quick_armature.py:405`) - a miss is a no-op with feedback, never a silent state change. A distinct option (clearing the parent to start a fresh root on an empty-space click) is rejected as a surprise: an empty-space click reads as "I missed," not "detach everything."

**Recommendation:** **(A) nearest tip within a pixel radius** for the hit-test, with the **no-reparent-on-miss** fallback. It reuses `region_event_to_xz_offset` and `nearest_index` (both already proven in the automesh pick path), keeps the pick tolerance screen-constant, matches the flat picture-plane model the rest of the modal commits to, and isolates the testable logic in the pure `nearest_index` so the headless test can assert "cursor near tip B picks B, cursor in empty space picks nothing." Pick-parent lives as the Reparent mode from decision 1; entering it via Tab, a hit sets `cls._last_bone_name` and (optionally) auto-returns to Draw so the natural next gesture is the chained drag. Surface the candidate tips and the live pick target in the existing GPU overlay (`_overlay.py` already draws session anchors and a parent-tail dashed line, so a Reparent-mode highlight is an additive draw branch, not a new handler). Size **M** (the pick resolver + setting `_last_bone_name` + a Reparent-mode overlay branch + the headless pick test); combined with decision 1 the whole feature is one **M-to-L** change, the heaviest interaction work in the open specs.

### 3. Preserving the locked Quick Armature UX promises

**Code anchors:** `decisions.md` "Quick Armature UX" and "Skeleton chrome and animation target"; the implementing code in `quick_armature.py`. Each locked promise is enumerated below with the code that owns it and why the mode layer leaves it intact.

**Question:** The redesign changes the interaction vocabulary. Does every promise the modal already commits to survive?

**The promises and how they survive:**

- **GPU preview line + the real bone on click, tail tracking MOUSEMOVE.** Owned by `_handle_mousemove` (`:275`) updating `cls._cursor_world`, `draw_preview_3d` (`_overlay.py:47`) drawing head -> cursor, and `_handle_leftmouse` (`:362`) committing the real bone on RELEASE. All of this is the Draw mode. The mode layer leaves Draw mode's PRESS / MOUSEMOVE / RELEASE path byte-for-byte; only a non-Draw mode reroutes LEFTMOUSE. **Survives unchanged.**
- **Tail tracks the mouse live.** Same `_handle_mousemove` -> `tag_redraw` loop (`:292`). Reparent mode adds its own MOUSEMOVE handling (to highlight the candidate tip), but does not touch Draw's. **Survives.**
- **Naming prefix from preference + F3 override.** Read once in `invoke` from the PG via `_sanitize_prefix` (`:200`), applied in `_create_bone` via `format_bone_name` (`:545`). The mode layer does not touch bone creation. **Survives.**
- **Front-Ortho auto-snap restores the prior view on exit (F3 opt-out).** Owned by `_snap_to_front_ortho` (`:655`), `_restore_view` (`:673`), and the `lock_to_front_ortho` operator property (`:95`), gated on the user not having orbited mid-modal (`view_pose_equal` at `viewport_math.py:163`). The mode layer never moves the camera; switching modes is a state flip, not a view op. **Survives.** Note: Reparent mode must use the same `mouse_event_to_plane_point` / `region_event_to_xz_offset` projection so a hit-test in a user-orbited view stays consistent with where bones were drawn.
- **Sweep the auto-created QuickRig on cancel only.** `_sweep_empty_armature` (`:775`) removes the rig only when `_created_armature_this_session` and it has zero bones. Reparent never creates bones, so a Tab into Reparent and back leaves the session-bone count untouched, and the sweep logic is unchanged. **Survives.**
- **Esc is labels-only; destructive cancel stays gated** ("Skeleton chrome and animation target" in `decisions.md`). The dynamic Esc label is in `emit_chord_layout` (`_status_bar.py:51`-`:54`), keyed on `cls._last_bone_name`. The mode-aware cheatsheet must keep this branch in whichever mode shows the exit hint. **Survives, with a note:** the per-mode status bar swap must not drop the session-state-aware Esc label.
- **The chord cheatsheet renders with real Blender event icons on the STATUSBAR.** Owned by `emit_chord_layout` (`_status_bar.py:23`) via the shared `chord` primitive. The mode layer turns the fixed seven-row list into a per-mode list (Draw rows vs Reparent rows), exactly as `emit_authoring_chord_layout` does per stage (`automesh_authoring.py:1307`). The icon-based rendering is unchanged. **Evolves, does not break.**

**Recommendation:** All seven promises survive because the mode layer is additive: Draw mode is the present behavior verbatim, and the new surface (the Tab handler, Reparent mode, the per-mode cheatsheet) sits beside it. The two watch-items are the **session-state-aware Esc label** (must persist into the mode-aware cheatsheet) and the **shared projection** (Reparent's hit-test must use the same Y=0 projection helpers so picks line up with drawn bones in any view). Both are constraints on the implementation, not new decisions. Size **S** for the verification itself - it is a checklist the headless test and a manual pass confirm, not new code beyond decisions 1 and 2.

## Verdict summary

**3 decisions, 0 ready to code.** The vocabulary call (decision 1) is the gate; decisions 2 and 3 are settled relative to it. Recommendation: a **mode-layer scheme** (Tab cycles Draw / Reparent; the status bar swaps per mode), reusing the `automesh_authoring.py` mode-dispatch + status-bar-swap architecture - this confirms the spec-050 lean and is now grounded in an in-repo precedent that already implements the per-mode routing, the ClassVar-driven status-bar repaint, and pixel-radius hit-testing. Pick-parent is the **Reparent mode**, resolving the hit-test by **nearest bone tip within a screen-constant pixel radius** (`region_event_to_xz_offset` + `nearest_index`), with **no reparent on a miss** (report and stay). Every locked Quick Armature promise survives because Draw mode is the current behavior unchanged and the mode layer is additive; the two implementation watch-items are the session-state Esc label and the shared Y=0 projection. Combined size is **M-to-L**, the heaviest interaction design of the open feature specs.
