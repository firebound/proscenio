# Spec 059: Skin coordination

Named attachment sets across slots, in the style of Spine skins: one switch swaps a chosen attachment per slot across many slots at once, so a character changes outfit, palette, or damage state in a single call instead of toggling each slot by hand. This is a coordination surface spanning three apps - the schema owns the named-set shape, the writer emits it, and Godot resolves it - and unlike every shipped feature it needs a layer the importer-only plugin deliberately does not have: a Godot runtime that re-routes attachment visibility after import. This spec decides the form, decides whether that runtime layer is warranted and where it lives, decides how a skin composes with the existing per-slot override, then builds the chosen form.

This spec is STUDY-first and is the heaviest and most speculative of the open features. Two of its three decisions are blocked, not just unmade: the first-class schema form rides the gated `format-migration-path` and is sequenced behind the storage-split spec (037), and the runtime layer reopens a core architectural call (`decisions.md` "No GDExtension / native runtime", "Conversion one-time, at editor import") that has held since the plugin's first cut. The honest output here is a recommended form plus a sequencing, not a shovel-ready TODO. Spine skins are the design precedent throughout: in Spine a skin is a named map from `(slot, attachment-key)` to a concrete attachment, and switching the active skin re-binds every slot the skin names at once - exactly the coordination this spec ports onto the slot system the codebase already ships.

## Scope

- **The form** - decide between a first-class `skins[]` array in the schema (rides the gated `format-migration-path`) and an additive form expressed through the existing generated-animations path (no migration, but borrows the animation machinery to carry a static selection).
- **The runtime layer** - decide whether applying a skin at runtime warrants the first piece of an actual Godot runtime in a plugin scoped import-only, and if so where it lives (a generated node, an opt-in helper script, or no runtime at all).
- **The override semantics** - decide how a per-slot attachment override (the `slot_attachment` visibility track that already ships) interacts with an active skin: which wins, and whether a skin switch clobbers a mid-animation override.
- **Wire the chosen form end to end** - schema, writer, Godot resolution, and an end-to-end fixture once the form and its dependencies are locked.

## Open decisions

### 1. The form: first-class `skins[]` versus the additive generated-animations path

**Code anchors:** `packages/models/src/proscenio_models/proscenio.py` (`Slot` is `name` / `attachments` / `bone` / `default`; `ProscenioDocument.format_version: Literal[1]`; `slots`, `animations` both `| None` optional top-level lists; the `Element` discriminated union and `MeshElement.polygons` are the two live "additive at format_version 1" precedents); `apps/blender/exporters/godot/writer/slot_emit.py` (`build_slot` / `_resolve_default` - a slot's `default` is the one piece of cross-attachment selection state today); `apps/blender/exporters/godot/writer/slot_animations.py` (`build_slot_animations` projects keyed `proscenio_slot_index` into a `slot_attachment` track - the existing path that already carries an attachment selection across time); `apps/godot/addons/proscenio/schema_bindings/proscenio_slot.gd` (the generated binding a new field would extend, with its `_set_fields` absent-vs-default machinery).

**Question:** A skin is a named map from each participating slot to one of that slot's `attachments[]` - structurally a second, named layer of the `default` that `Slot` already carries. Where does that map live: a new first-class `skins[]` document field, or piggybacked on the `animations[]` path as a degenerate single-key `slot_attachment` selection per slot?

**Options:**
- **(A) First-class `skins[]` in the schema.** A top-level `skins: list[Skin] | None`, each `Skin` a `name` plus a `slot -> attachment` map (mirroring Spine's skin model directly). Clean, self-describing, queryable, and the natural home for the concept. But a new required-shape array is a breaking schema change by the locked rule (`decisions.md` "Schemas are the contract": post-launch, every cross-component shape change is bump-plus-migration), so it rides `format-migration-path` (gated) and the storage-split window (037) rather than landing additively. Pre-launch it *could* land in place at `format_version=1` under the current "no bump" rule, but only if the whole skin feature ships before the first public tag - which collides with the runtime-layer decision below being the slowest part.
- **(B) Additive form via the generated-animations path.** Express each skin as an `Animation` whose tracks are single-key `slot_attachment` selections, one per participating slot, naming the chosen attachment at `time=0`. This reuses the shipped `slot_attachment` track end to end (writer `slot_animations.py`, the `Track` / `Key` models, the Godot `_add_slot_attachment_tracks` resolver) and is additive - `animations[]` is already optional and the track type already exists, so no importer reads anything new. No migration, no schema bump. The cost is semantic: a skin is not an animation, and modelling it as a zero-length animation means a skin switch is "seek an AnimationPlayer to a one-frame clip," which fights the per-slot override (decision 3) because both drive the same `visible` channel, and leans on AnimationPlayer state for what is really a static binding.
- **(C) Additive `default`-set form (a lighter A).** Instead of a full `slot -> attachment` map per skin, model a skin as a named override of each slot's `default` only, stored as an additive optional field on `Slot` (`Slot.skins: dict[str, str] | None`, skin-name to attachment) rather than a new top-level array. Additive-at-v1 like `MeshElement.polygons` and `modulate` (no migration), keeps the selection where `default` already lives, and resolves at import to the same starting-visibility computation `resolve_sprite_parent` already does. The cost is it is not Spine-shaped (the map is inverted - per slot rather than per skin), so authoring and docs read less naturally, and a skin that touches few slots still pays a field on every slot.

**Recommendation:** **(A) is the correct destination; (C) is the cheaper additive bridge if the feature must ship before the migration gate; (B) is not recommended.** (A) matches the precedent (Spine's own model) and is the only form that reads cleanly, but it is gated - it cannot land before `format-migration-path` fires and the storage split (037) opens the breaking-change window, per `decisions.md` "Schemas are the contract" and the 037 verdict. (B) is rejected: it conflates a static binding with an animation, and it collides head-on with decision 3 by driving attachment `visible` from two systems (a skin "animation" and a real `slot_attachment` override track) with no defined precedence - exactly the runtime fragility the backlog entry flags. (C) is the honest interim: it carries the feature additively at `format_version=1` (no gate) by extending `Slot` the way `polygon`s and `modulate` extended their models, at the cost of an inverted, less Spine-like shape. **Decide (A) vs (C) by whether this ships before or after the migration gate opens; if after, collapse to (A).** Size **L** for (A) (schema + migrator coupling + writer + binding + Godot resolve + fixture), **M** for (C) (additive field + writer + resolve), **S** for (B) and not worth the semantic debt.

### 2. The runtime layer: does applying a skin warrant Godot's first runtime piece, and where does it live?

**Code anchors:** `apps/godot/addons/proscenio/plugin.gd` (the entire plugin is one `EditorImportPlugin` added in `_enter_tree` - no autoload, no `add_autoload_singleton`, no `_process`); `apps/godot/addons/proscenio/importer.gd` (`_import` bakes a `PackedScene` of plain nodes and the plugin's job ends there); `apps/godot/addons/proscenio/builders/sprite_attach_util.gd` (`resolve_sprite_parent` sets `visible = sanitized_name == slot_info.default` at *build* time - the only place attachment visibility is decided today, and it runs once, at import); `apps/godot/addons/proscenio/builders/slot_builder.gd` (`SlotInfo.default` is baked into the scene and then discarded - nothing carries the slot's attachment list or default into the runtime scene); `apps/godot/addons/proscenio/builders/animation_builder.gd` (`_add_slot_attachment_tracks` - the one mechanism that flips attachment `visible` *after* import, and it does so through AnimationPlayer, which is Godot core, not plugin runtime). Locked context: `decisions.md` "No GDExtension / native runtime" and "Conversion one-time, at editor import" (the generated `.scn` runs on plain Godot 4 with the plugin uninstalled), whose revisit triggers explicitly include "Deep Firebound integration" and a "Blender <-> Godot live-link" but not skin switching.

**Question:** "Switch the active skin at runtime" means, after import, re-deciding `visible` for every attachment under every named slot. Nothing in the imported scene can do that today: `resolve_sprite_parent` decides visibility once at import and throws away the slot's attachment list and default; the only post-import visibility mechanism is an AnimationPlayer `slot_attachment` track, which is per-slot and time-keyed, not a named cross-slot set. So a skin switch needs *something* in the running scene to hold the skin map and apply it. Is that the first crack in the import-only wall, and where does it sit?

**Options:**
- **(A) No runtime - bake skins into selectable AnimationPlayer clips.** Each skin becomes a named one-frame animation (the decision-1 (B) shape); "switch skin" is `player.play("skin_name")` or a seek. Zero new runtime: it reuses AnimationPlayer (Godot core), so the plugin stays import-only and the scene still runs with the plugin uninstalled. But it inherits all of decision-1 (B)'s problems, and worse, it owns the AnimationPlayer for skin state, so a skin clip and a gameplay clip cannot both drive attachment visibility without an AnimationTree blend the importer would have to author. This keeps the architecture pure at the cost of a fragile, surprising API.
- **(B) A generated runtime node baked into every character.** Emit a small `ProscenioSkinController` (a `Node` script) as a child of the character root, carrying the skin map as exported data and exposing `set_skin(name)` that walks the slot Node2Ds and re-applies `visible`. This is the cleanest API and the true Spine-runtime shape, but it is unambiguously the first piece of a Godot runtime in an import-only plugin: the baked scene would now depend on a plugin script (or a copied-in script) to run, breaking "runs on plain Godot 4 with the plugin uninstalled" unless the script is vendored into the output. That directly reopens `decisions.md` "No GDExtension / native runtime" - which is a deliberate, load-bearing call, not an oversight.
- **(C) An opt-in helper script the game attaches, plus enough baked metadata to drive it.** The importer bakes the skin map as plain data into the scene (an exported dictionary on the slot nodes or root, no behavior), and ships a *separate, optional* `ProscenioSkin.gd` helper in the addon that a game author attaches or instances themselves to call `set_skin`. The scene still runs with the plugin uninstalled (the data is inert; nothing references the helper unless the game opts in), so the import-only guarantee holds for the generated artifact, and the runtime lives outside the generated scene as a convenience the user adopts deliberately. The cost is it is not automatic - the game wires it - and it requires baking the slot-to-attachment metadata the current importer discards.
- **(D) Defer the runtime entirely; ship the schema/writer form only.** Land the form (decision 1) and emit it, so the data round-trips and is queryable, but ship no application mechanism - document that runtime skin switching awaits the runtime decision. Honest about the gate, but delivers a half-feature (data with no consumer), which the project's own "no field without a consumer" discipline (cf. the gated Photoshop tag entries) argues against shipping.

**Recommendation:** **(C) baked metadata plus an opt-in helper, with (A) as the no-runtime fallback if even an optional helper is judged out of scope.** (C) is the only option that delivers a real `set_skin(name)` API *and* preserves the locked guarantee that the generated `.scn` runs on plain Godot 4 with the plugin uninstalled: the generated scene carries inert data, and the behavior is a separate addon script the game adopts on purpose - a convenience, not a dependency baked into the artifact. (B) is the nicest API but reopens "No GDExtension / native runtime" by making the baked scene depend on plugin code to function, which is a core-architecture revisit this spec should not make unilaterally - flag it, do not assume it. (A) keeps the architecture perfectly pure but pays for it with the fragile AnimationPlayer-as-skin-store API and the decision-3 collision; keep it only as the fallback if (C)'s optional helper is rejected. (D) is not enough on its own. Either way, **note the prerequisite: the importer must start baking the slot-to-attachment metadata it currently discards in `slot_builder.gd` (`SlotInfo.default` and the attachment list never reach the runtime scene)** - that baking is shared groundwork for (A), (B), and (C). Size **M** for (C) (bake metadata + the opt-in helper + tests), **M-L** for (B) (same plus the architecture-revisit cost), **S-M** for (A) (clip authoring + the AnimationTree caveat).

### 3. The override semantics: how a per-slot attachment override composes with an active skin

**Code anchors:** `apps/godot/addons/proscenio/builders/animation_builder.gd` (`_add_slot_attachment_tracks` - per-slot, per-key `visible` flips at NEAREST interpolation, the shipped per-slot override; `decisions.md` "Slot system": "Hard cut, NEAREST interp on `slot_attachment` tracks"); `apps/blender/exporters/godot/writer/slot_animations.py` (`_build_slot_attachment_track` - one `slot_attachment` track per slot from keyed `proscenio_slot_index`, the authoring side of an override); `apps/godot/addons/proscenio/builders/sprite_attach_util.gd` (`resolve_sprite_parent` - the build-time visibility baseline a skin and an override both ultimately rewrite, the single channel both contend for: `visible`); `apps/blender/exporters/godot/writer/slot_emit.py` (`_resolve_default` - the priority logic that already arbitrates "explicit choice vs fallback" for one slot, the natural template for skin-vs-override precedence). Locked context: `decisions.md` "Slot system" (slots are kind-agnostic, attachments are a name list cross-referenced from `sprites[]`).

**Question:** A skin sets attachment visibility per slot; a `slot_attachment` animation track *also* sets attachment visibility per slot, per key. Both write the same `visible` channel. When a skin is active and an animation track flips an attachment on the same slot - or when a skin is switched mid-animation - what is the resulting visibility, and is it deterministic? Spine answers this explicitly (the active skin provides the attachment a slot resolves to *unless* an animation keys a specific attachment, which wins for the keyed interval); the codebase has no answer because skins do not exist yet.

**Options:**
- **(A) Animation override wins while keyed; skin provides the resting binding (Spine's rule).** A skin sets each slot's baseline visible attachment; a `slot_attachment` track overrides that slot for its keyed span, then the slot reverts to the skin's choice. This matches Spine and matches author intuition (an animation that punches in a "hurt" attachment should win over the resting outfit), and it mirrors `_resolve_default`'s existing "explicit choice beats fallback" shape. The cost is it demands real composition logic in whatever applies the skin (decision 2): the runtime must know which slots an animation currently controls and not stomp them - non-trivial against Godot's `visible` being a single boolean per node with no layering.
- **(B) Skin wins; switching skin re-asserts visibility unconditionally.** `set_skin` hard-sets every named slot's visibility to the skin's choice, clobbering any in-flight override. Dead simple to implement (just re-run the baseline computation), but it means switching outfit mid-attack visibly resets the attack's swapped attachment - surprising, and it makes skins and attachment animations mutually exclusive in practice.
- **(C) Forbid the overlap - a slot is skin-driven or animation-driven, not both, validated at export.** The Blender validator (the lazy-inline pattern, `decisions.md` "Validation is lazy + inline") errors when a slot appears in both a skin and a `slot_attachment` track, forcing the author to pick one model per slot. Sidesteps the runtime composition problem entirely and fits the project's preference for catching contradictions at export over resolving them at runtime, but it removes a legitimate Spine workflow (a skin for the outfit, an animation for transient swaps on the same slot).

**Recommendation:** **(A) is the correct target semantics; (C) is the pragmatic first cut that defers (A)'s runtime cost.** (A) is what Spine does and what authors will expect, and it reuses the "explicit beats baseline" shape `_resolve_default` already encodes - but it is only affordable once decision 2 lands a runtime that can track per-slot animation ownership, so it is gated on that. (C) is the right *first* answer: an export-time validator error when a slot is claimed by both a skin and a `slot_attachment` track keeps the two systems non-overlapping, costs only a validator check (the cheapest layer), and fits "Validation is lazy + inline" exactly - it ships the feature without the hard runtime composition, and (A) becomes a later relaxation when a real workflow needs the overlap. (B) is rejected: clobbering in-flight overrides is the surprising behavior the backlog's "fragile under attachment overrides" warning is pointing at. **Ship (C), document (A) as the planned relaxation.** Size **S** for (C) (one validator check over slots-in-skins-vs-slots-in-tracks), **M-L** for (A) (runtime per-slot ownership tracking, gated on decision 2's runtime existing).

## Verdict summary

**3 decisions, 0 ready to code - this spec is gated and sequenced, not shovel-ready.** The form (decision 1) wants first-class `skins[]` (A) as its destination, but that rides the gated `format-migration-path` and the storage-split window (037); the additive `Slot.skins` bridge (C) is the only form that can land pre-gate, at the cost of a less Spine-like shape. The runtime layer (decision 2) is the genuine architectural fork: a real `set_skin` API needs *something* in the running scene, and the recommendation - baked inert metadata plus an opt-in helper script (C) - is the only route that keeps the locked "runs on plain Godot 4 with the plugin uninstalled" guarantee intact while still delivering an API; a generated runtime node (B) is nicer but reopens "No GDExtension / native runtime" and must not be assumed here. The override semantics (decision 3) target Spine's "animation overrides skin while keyed" (A) but ship first as an export-time "a slot is skin-driven or animation-driven, not both" validator (C), deferring the runtime composition cost. Sequencing, not a build order: (1) land the slot-metadata baking groundwork (shared by every runtime option) on the next Godot-builder touch; (2) ship the additive `Slot.skins` form (C) plus the opt-in helper (C) plus the validator guard (C) as a coherent pre-gate cut, OR (3) wait for the `format-migration-path` gate and the 037 window, then ship first-class `skins[]` (A) with the same runtime/override choices. Do not start before either the gate opens (for the first-class form) or the team accepts the additive bridge and the opt-in-helper scope expansion (for the pre-gate cut). The dependency on 037 and the format-migration gate is real and load-bearing; this STUDY marks the decision and the sequencing, and the TODO finalizes once the form is locked and the dependency resolves.
