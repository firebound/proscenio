# Spec 064: Help copy and docs alignment

The in-Blender help popups (the `?` button on every panel and subpanel) and the Docusaurus reference site grew independently, and three seams now disagree. The popup is drawn at a fixed `480` px width while its prose is greedily wrapped to a fixed `72` characters, so every help body floats in a popup wider than the text it fills, leaving the right band empty (the reported visual defect). The help bodies themselves were written before the two-tier panel structure settled, so a panel topic and its subpanels repeat each other and a panel `?` reads as detailed as a subpanel `?` instead of giving a shallow "what this panel is for" overview. And four topics have no doc home at all (`pipeline_overview`, `sprite_bone_parent`, `sprite_frame_preview`, `pose_library`), so their popups show no `Open online docs` button while the rest deep-link into the site. This spec settles the help-copy contract at three tiers (popup geometry, two-tier copy, doc deep-link), rewrites the copy to it, aligns the docs site so every panel owns a page and every subpanel owns a section the tooltip points at, and leaves the strings in a translation-stable shape so the gated i18n table can be populated on demand without re-churning the copy.

This spec is STUDY-first. The geometry fix is objective and lands first. The copy contract and the doc mapping are coupled design calls (the copy tier decides how much lives in the popup versus the page), and the i18n-readiness call decides how the rewritten strings are structured so the [`gated.md`](../gated.md) `i18n-locale-tables` item is unblocked rather than re-opened later.

## Scope

- Reconcile the popup geometry so the drawn width matches the wrapped text extent (kill the empty right band).
- Define and apply a two-tier copy contract: a panel `?` gives a shallow overview of what the panel is for and why it exists; a subpanel `?` is focused only on its own feature, with no repetition of the parent; deeper specifics move to the site.
- Establish one canonical mapping (panel/subpanel -> help topic -> doc path), tested both directions, and resolve the four unmapped topics and the `Validate` page-versus-section mismatch.
- Align the docs site so every panel has a page and every subpanel has a section the tooltip `Open online docs` button deep-links to; deepen the thin panel-only pages.
- Leave the help strings translation-stable (one msgid per body, registered per topic) so the gated i18n table can be populated later without a second copy pass. Do not populate any locale now.
- Out of scope: addon screenshots (stays the [`gated.md`](../gated.md) `addon-docs-screenshots` item, frozen until a 1.0 panel-layout freeze); populating a non-English locale (stays the gated `i18n-locale-tables` item, this spec only unblocks its trigger); the `SpritePayload -> ElementPayload` validator rename (stays the gated `validator-element-rename` item).

## Open decisions

### 1. Popup geometry: reconcile drawn width with wrapped text extent

**Code anchors:** `apps/blender/core/help_topics.py:33-40` (the two constants that disagree: `POPUP_WIDTH = 480` px and `POPUP_WRAP_CHARS = 72`, the second with a comment noting the old hand-wrapping sat near 55 chars and "left the right third of the popup empty" - the fix overshot the other way); `apps/blender/operators/help_dispatch.py:70-72` (`invoke_popup(self, width=POPUP_WIDTH)` - the only consumer of the px width); `apps/blender/core/help_topics.py:87-109` (`reflow_paragraph` - the greedy word-wrap that consumes `POPUP_WRAP_CHARS`); `apps/blender/operators/help_dispatch.py:77-107` (the draw loop that reflows summary + every section body and emits one `layout.label` per line).

**Question:** Blender exposes no draw-time text metrics inside a popup (the file comment states this), so the popup width and the wrap budget are two independent guesses that currently disagree: `480` px holds roughly 90 characters at default UI scale, but the prose wraps at `72`, so each line stops about a fifth short of the right edge. The two numbers must be tied so they cannot drift, and the result must degrade gracefully under non-default UI scale (where underflow - text narrower than the popup - is cosmetic, but overflow - text clipped past the popup edge - is a real defect).

**Options:**
- **(A) Shrink `POPUP_WIDTH` to the 72-char extent.** Pick the px width that 72 characters fill at default scale (~ `380` px) so the popup hugs the existing wrap. One constant change, no draw-loop change, directly removes the band. The width and wrap still live as two hand-tuned numbers, so a future copy or wrap edit can re-introduce the gap. Size **S**.
- **(B) Raise `POPUP_WRAP_CHARS` to fill 480.** Widen the wrap (~ `90` chars) so lines reach the current popup edge. Keeps the larger popup, but pushes the failure mode toward overflow: at higher UI scale 90 characters no longer fit `480` px and lines clip. Trades a cosmetic underflow for a functional overflow. Size **S**.
- **(C) Derive one from the other through a single px-per-char constant.** Introduce `_PX_PER_CHAR` and define `POPUP_WIDTH = POPUP_WRAP_CHARS * _PX_PER_CHAR + padding`, so the drawn width is always the wrapped extent by construction and the two can never disagree again. Choosing the wrap budget (the readability lever, ~ `72`) then fixes the geometry. Deterministic and unit-testable (assert the derived width tracks the wrap); no per-draw cost. Size **S**.
- **(D) Measure the longest reflowed line per draw and size the popup to it.** `invoke` would reflow first, find the max line length, and pass `max_len * _PX_PER_CHAR` as the popup width, so a short topic gets a narrow popup and a long one a wide one. Tightest possible fit, but `invoke_popup` width is set before `draw` runs, so this needs the reflow hoisted into `invoke`, and per-topic popup width is visually inconsistent across the `?` buttons. Size **M**.

**Recommendation:** **(C).** The defect is precisely that two numbers meant to describe the same extent were tuned independently; binding them through one px-per-char constant makes the band structurally impossible and leaves a single readability knob (the wrap budget). It is testable in the bpy-free core (`POPUP_WIDTH` becomes a computed module constant, asserted against the wrap), costs nothing at draw time, and keeps a uniform popup size across all topics (rejecting D's per-topic variance). Set the wrap budget from the rewritten copy in Decision 2 - shorter bodies may want a slightly narrower popup - but lock the relationship now. Size **S**.

### 2. The two-tier copy contract: panel intent versus subpanel specifics

**Code anchors:** `apps/blender/core/help_topics.py:43-61` (the `HelpSection` and `HelpTopic` dataclasses: `title`, `summary`, `sections` tuple, `see_also`, `doc_url` - the shape every topic is authored in); `apps/blender/core/help_topics.py:112-916` (the 32 registered topics, panel topics and subpanel topics authored in the same multi-section shape with no tier distinction); `apps/blender/panels/_helpers.py:100-156` (`draw_subpanel_header` / `draw_subbox_header` / `draw_help_button` - the three `?` wirings, all passing a flat `help_topic` id with no tier marker). Tier owners: panel topics are `pipeline_overview`, `outliner`, `active_element`, `slot_system`, `skeleton`, `mesh_generation`, `weight_paint`, `animation`, `atlas`, `helpers`; the rest are subpanel topics.

**Question:** A panel `?` and its subpanels' `?` were written at the same depth, so a reader who opens the `Skeleton` panel help gets armature/pose/quick-armature detail that repeats what the three subpanel helps already say, and the panel help never answers the simpler question a panel `?` should answer first: what is this panel for and when do I reach for it. The contract needs to state what each tier says, and how repetition is prevented, before the rewrite.

**Options:**
- **(A) Strict two-tier shape, enforced.** A panel topic is one short overview paragraph (the panel's intent and the stage of the pipeline it serves) plus the `Open online docs` link, with `sections = ()` - it does not enumerate its subpanels' features. A subpanel topic is one summary paragraph plus at most one tight focused section, scoped strictly to that subpanel's own controls, naming the parent only by reference ("part of Weight Paint") not by re-explaining it. A shape test asserts panel topics carry no `sections` and stay under a character budget, and that no subpanel body repeats its parent's summary. Deeper, longer specifics live only on the site. Size **M** (the rewrite of 32 bodies plus the guard).
- **(B) Soft tiering, edit for concision only.** Keep the current `summary + sections` shape for all topics, just trim each body and remove the worst duplication by hand. No structural rule, no test. Fastest, but the tiers stay implicit and drift back the next time a topic is edited, and "panel help reads like subpanel help" returns. Size **S-M**.
- **(C) Collapse panel topics into a single shared overview.** Replace the ten panel topics with links into the pipeline overview, so a panel `?` always opens the same map with the current panel highlighted. Minimal copy, but loses the per-panel "what is this for" answer and over-couples every panel to one growing topic. Size **S**.

**Recommendation:** **(A).** The reported problem is exactly that the tiers are not distinguished, so the fix is to make the distinction explicit and testable, not advisory (rejecting B's drift) and not flattened away (rejecting C's loss of per-panel intent). Panel `?` answers "what and why" in one paragraph and sends depth to the page; subpanel `?` answers "this control, specifically" with no parent re-explanation; the site carries the worked detail. Encode the rule as a shape test in the bpy-free core so a future topic edit cannot silently break the tier. This contract also sets the wrap budget for Decision 1 (shorter bodies). Size **M**.

### 3. Canonical panel/subpanel -> topic -> doc mapping, and the Validate mismatch

**Code anchors:** `apps/blender/core/help_topics.py:923-970` (`_DOCS_BASE`, the `_DOC_PATHS` dict mapping 28 of 32 topic ids to a relative doc path, and `topic_for` which fills `doc_url` from the base - the four ids absent from `_DOC_PATHS` get no `Open online docs` button: `pipeline_overview`, `sprite_bone_parent`, `sprite_frame_preview`, `pose_library`); `docs/02-blender-addon/` (the 11 reference pages); `apps/docs/sidebars.ts:30-56` (the explicit `toolsSidebar` page list); the panel-to-topic wiring catalogued across `apps/blender/panels/*.py` (every `draw_subpanel_header(..., feature_id, help_topic)` call). Confirmed already-correct sections: `element.md` H2s match the five Element subpanels; `skeleton.md`, `weight-paint.md`, `mesh-generation.md`, `slots.md` sections match their subpanels. Confirmed gaps: `pipeline.md` has `#import` and `#export` but no `#validate` (validation is a standalone `09-validation.md` page while `Validate` is a subpanel of the `Pipeline` panel); `pose_library` (the `Save Pose to Library` button on the Pose Mode row) has no doc section; `sprite_frame_preview` (the preview-material helper) has no doc home; `sprite_bone_parent` ("Attach to Bone") already has an `element.md` `## Attach to Bone` section but is not mapped to it.

**Question (locked by the user):** The docs structure must mirror the Blender panel tree exactly - a panel is a page, a subpanel is a section, one-to-one, with no exceptions. The mapping is mostly already that, but it lives as a hand-maintained `_DOC_PATHS` dict with no test tying it to the panels or the doc headings, four topics fall through, and one place breaks the mirror: the `Pipeline` panel's three subpanels split across two doc pages (Import/Export as sections of `pipeline.md`, but Validate as its own standalone `09-validation.md` page). The mirror directive resolves the split (Validate becomes a section); the only open part is where the canonical mapping lives and how it is kept honest.

**Locked structural rule (the exact mirror).** Every top-level panel owns one page; every subpanel owns one H2 section under its parent panel's page; the About footer panel owns the index page (`/blender-addon/`, the overview that also hosts the status-badge legend). A topic that is neither a panel nor a subpanel (`status_legend`, `pose_library`, `sprite_frame_preview`) does not get a page or a top-level section - it is an anchor inside its host subpanel's section, or it is demoted to the button's `bl_description`. The resulting page set is exactly the ten panels plus the index: `pipeline`, `outliner`, `element`, `slots`, `skeleton`, `mesh-generation`, `weight-paint`, `animation`, `atlas`, `helpers`, and `index`. `09-validation.md` folds into `pipeline.md#validate`; the standalone page and its sidebar entry are removed with a redirect from the old slug, and its two H2s (`Errors block the export`, `Warnings inform but still export`) demote to H3 under `#validate`.

**Options for the mapping home:**
- **(A) One source-of-truth table plus a two-way coverage test.** Keep `_DOC_PATHS` as the single map but add a test that asserts, in both directions, that the table IS the exact mirror: every panel `?` points at a topic whose doc path is the bare panel page; every subpanel `?` points at a topic whose doc path is `<parent-page>#<subpanel-anchor>`; every panel page H2 has a subpanel topic pointing at it and vice versa; every doc path resolves to a real page-or-anchor; and the page set equals the panel set exactly (no extra pages, no missing ones). Extends the existing reverse-coverage test (spec 036 added one for orphan topics). Cheap, catches drift, no new structure. Size **S**.
- **(B) Derive `_DOC_PATHS` from the panel registry.** Generate the topic-to-path map from the panel/subpanel tree so it cannot disagree with the panels by construction. Removes the dict, and since the rule is now a strict mirror this is a closer fit than before - the path of a subpanel topic is mechanically `<parent>#<slug(bl_label)>`. Still needs a test that the doc headings actually exist, and couples doc routing to panel internals. Size **M**.

**Recommendation:** **(A).** The mirror is now a hard structural law, so the highest-value move is a test that enforces it both directions against a single visible map, rather than generating the map from panel internals (B) where a heading typo still slips through and the routing becomes implicit. Keep `_DOC_PATHS` as the one readable source and let the coverage test assert it equals the panel-tree mirror exactly. Map the orphans onto the mirror: `pipeline_overview -> pipeline` (it is the Pipeline panel's own topic, not a separate overview), the About/index page carries no popup topic of its own beyond `status_legend -> index#status-badges`, `sprite_bone_parent -> element#attach-to-bone` (section exists), `validation -> pipeline#validate` (after the fold), and resolve `pose_library` / `sprite_frame_preview` as host-section anchors or `bl_description` per Decision 5. Size **S** for the test, the fold, and the mappings.

### 4. i18n readiness: structure the strings, do not populate

**Code anchors:** `apps/blender/core/i18n.py` (registers an empty `TRANSLATIONS` against `bpy.app.translations`; the [`gated.md`](../gated.md) `i18n-locale-tables` item notes "populating means translating every label and multi-line help body" and warns "never populate before a copy-churn spec lands"); `apps/blender/core/help_topics.py:43-61` (help bodies are plain Python strings on the dataclasses, drawn via `layout.label` which does not pass through Blender's translation lookup the way `bl_label` does); `apps/blender/operators/help_dispatch.py:77-107` (the draw loop emits each reflowed line as a literal `layout.label(text=...)`).

**Question:** This spec is the "copy-churn spec" the gated item is waiting for, so it should leave the rewritten copy in a shape a translator can fill without a second editorial pass. The decision is how far to take i18n now: structure-only (make each body a single translatable unit with a stable context) versus also populating a locale.

**Options:**
- **(A) Structure-only, leave the table empty.** Author each help body as one whole-string msgid per topic section (no sentence built by f-string concatenation, which fragments a string a translator cannot reassemble), assign each a stable translation context (the topic id), and route the popup draw and panel labels through the existing translation lookup so a populated table would take effect. Then update the gated `i18n-locale-tables` trigger to record that the copy-churn prerequisite is met and a locale can be added on first request. No locale shipped, no ongoing re-maintenance. Size **M**.
- **(B) Structure plus a seed locale (PT-BR).** Do (A) and populate one locale as proof. Demonstrates the path end-to-end but takes on the re-maintenance the gated note explicitly defers (every future copy edit must update the table) for a locale with no logged demand, and the docs site is English-only so the translation would be half a story. Size **L**.
- **(C) i18n out of scope.** Rewrite the strings as plain literals and leave i18n structure for whenever the gated item triggers. Cheapest now, but the gated item then re-opens the entire copy to restructure it for translation - exactly the second churn this spec is positioned to prevent. Size **S** now, **re-churn later**.

**Recommendation:** **(A).** The whole reason `i18n-locale-tables` is gated behind "a copy-churn spec" is to avoid restructuring the copy twice; doing the rewrite (Decision 2) without making it translation-stable wastes that positioning (rejecting C). Populating a locale (B) takes on maintenance for demand that does not exist and that the docs site cannot match. So make the strings translatable units with stable contexts, wire the lookup, leave `TRANSLATIONS` empty, and rewrite the gated trigger to "copy-churn spec 064 landed; populate on first non-English request." Size **M**.

### 5. The two remaining orphan topics: doc home or drop

**Code anchors:** `apps/blender/panels/skeleton.py:227-260` (the `pose_library` `?` is an extra help button on the `Save Pose to Library` row inside the Pose Mode subpanel, not a panel/subpanel header - so it has no natural page-or-section of its own); the `sprite_frame_preview` topic (the preview-material helper, re-wired behind the spec 036 reverse-coverage test, with no panel header currently hosting it as a primary `?`); `apps/blender/core/help_topics.py:923-954` (`_DOC_PATHS`, where both are absent).

**Question:** `pose_library` and `sprite_frame_preview` are the two topics that are not a panel and not a subpanel - they hang off a row button or a helper. The exact-mirror rule (Decision 3) forbids them a page or a top-level section, and the two-way coverage test will fail on them unless they are either anchored inside a host subpanel section or retired to a `bl_description`. Decide per topic.

**Options:**
- **(A) Anchor each inside its host subpanel section.** `pose_library` lives in the Pose Mode subpanel, so its body becomes an anchored sub-part of `skeleton#pose-mode` (an inline `#save-pose-to-library` anchor inside that section, not a sibling H2), and its topic `doc_url` deep-links there. `sprite_frame_preview` anchors inside whichever subpanel surfaces it. Keeps both helps and the deep-link, adds no top-level section, honors the mirror.
- **(B) Demote both to native tooltips, drop the popup topics.** Move each explanation to the button's `bl_description` (the native hover tooltip) and remove the topic, so the coverage test only governs panel/subpanel topics. Least doc surface; loses the deep-link and the longer body.
- **(C) Mixed.** Decide per topic at rewrite time - anchor the one with real depth (option A), demote the thin one to `bl_description` (option B).

**Recommendation:** **(C), leaning (A) for `pose_library`.** `Save Pose to Library` is a real authoring action worth a body, so anchor it inside `skeleton#pose-mode` (an in-section `#save-pose-to-library` anchor, never a sibling H2 - the mirror reserves H2s for subpanels). `sprite_frame_preview` is a preview convenience; if the rewrite finds its body is one sentence, demote it to `bl_description` and drop the topic so coverage stays clean, otherwise anchor it inside its host subpanel section too. Neither becomes a page or a top-level section. Make the call during the Decision 2 rewrite when each body's real weight is visible. Size **S**.

## Extra suggestions (accepted into scope where cheap)

- **Two-way coverage test as the keystone.** The single highest-value addition: one test that fails CI if a panel `?` points at an unregistered topic, a topic has no doc path, a doc path 404s against the page/anchor set, or a panel-page H2 has no topic pointing at it. It turns "the tooltips and the docs agree" from a manual audit into a check. Folded into Decision 3 (A).
- **Terminology guard.** The copy must use the `Element` vocabulary (not the legacy `Sprite` where `Element` is meant) and must keep the three weight operations distinct (automesh regen preserves weights; PSD re-import loses them; re-rig loses them) per the project's standing distinction - conflating them has caused doc bugs before. Add the weight-ops distinction to the canonical doc home and have the copy reference it rather than re-explain it.
- **Consolidate the lone inline URL.** `import_photoshop` carries a raw GitHub tree URL in `see_also`; fold the example reference into the doc page and keep the popup `see_also` for doc deep-links only, so every outbound link from a popup goes through the `_DOCS_BASE` pattern.
- **Deepen the thin panel-only pages.** `outliner.md`, `animation.md`, `atlas.md`, `helpers.md` are panel pages with no H2s; the two-tier contract pushes their depth onto these pages, so each gains the worked detail the popup now omits. This is the bulk of the docs work.
- **Status-badge legend single home.** `status_legend` deep-links to the index `#status-badges`; confirm that anchor is the one canonical explanation and that the panel-status icons reference it rather than re-listing the badges.
- **Out-of-scope but adjacent, noted for the trigger:** screenshots (`addon-docs-screenshots`) and the `SpritePayload -> ElementPayload` rename (`validator-element-rename`) stay gated; this spec touches neither but its terminology guard makes the rename's eventual landing a pure mechanical change.

## Verdict summary

**5 decisions; combined size M-L across roughly five PRs, code and docs split per the repository's commit rules.** Decision 1: bind the popup width to the wrap budget through one px-per-char constant so the empty-band defect is structurally impossible (option C), lands first as an objective fix. Decision 2: a strict, tested two-tier copy contract - panel `?` is a one-paragraph "what and why," subpanel `?` is focused on its own controls with no parent repetition, depth moves to the site (option A). Decision 3 is locked by the user as a hard structural law: the docs mirror the Blender panel tree exactly - panel is a page, subpanel is a section, no exceptions - so `validation` folds from a standalone page into `pipeline#validate`, the page set equals the ten panels plus the index, and a single `_DOC_PATHS` map is held to that mirror by a two-way coverage test (option A for the home). Decision 4: structure every help body as a translation-stable unit and wire the lookup but leave the locale table empty, unblocking the gated i18n item rather than populating it (option A). Decision 5: anchor `pose_library` inside `skeleton#pose-mode` (never a sibling H2, the mirror reserves H2s for subpanels) and decide `sprite_frame_preview` (in-section anchor versus `bl_description`) at rewrite time (option C). The objective geometry fix and the coverage test are code (branch + PR); the copy rewrite is code in `core/help_topics.py` (branch + PR) but the docs-site pages and these spec files commit direct to main per the docs convention. Once the calls are locked they move to [`decisions.md`](../decisions.md) and the implementable rows become [TODO.md](TODO.md).
