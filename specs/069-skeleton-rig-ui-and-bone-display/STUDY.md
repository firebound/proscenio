# Spec 069: Skeleton Rig UI and bone display

The Skeleton panel's Active Armature subpanel today lists bones with a left-aligned name, an IK cue, and a right-side text read-out of connectivity ("connected" / "disconnected" / "relative"). That text is noisy, carries no tooltip, and the list keeps a single source order with no alphabetical alternative and no way to pin the bones a rigger touches most. At the same time the panel has no equivalent of a Rigify-style Rig UI - a compact grid of per-group buttons that select a control set and toggle its visibility - even though Blender's native bone collections (4.1+ nested) already hold exactly the grouping such a UI would read. This spec reworks the bone list into a polished, sortable surface with per-bone favorites and adds a Rig UI subpanel driven by the armature's native bone collections, then folds in the armature-wide display controls and the per-collection color / custom-shape batch operations that the same collection-iteration primitive unlocks.

These goals share one spec because they all live on the picked armature and reuse two primitives: the Outliner's hierarchy-vs-flat sort and favorites chrome (spec 043 / 036), which the bone list mirrors verbatim, and a single "iterate the bones of a collection" helper that the Rig UI selection, the per-collection color, and the custom-shape assignment all call. Splitting them would duplicate that helper three ways and re-derive the sort/favorites pattern the Outliner already proved.

## Scope

- **A. Connectivity icons + tooltips** - replace the right-side connectivity text with Blender icons (`LINKED` / `UNLINKED` / `CON_CHILDOF`) carrying hover tooltips. Connected/disconnected is read-only information only; relative parenting is a live toggle.
- **B. Hierarchy / flat-alphabetical sort** - the bone list keeps the parenting-tree order (indented) by default and collapses to a flat alphabetical order when the native A-Z toggle is on, mirroring the Outliner exactly.
- **C. Per-bone favorites** - a star column pins bones; a Favorites filter narrows the list to pinned bones. Storage is a new `PropertyGroup` on `bpy.types.Bone`, mirroring the per-Object favorite.
- **D. Rig UI subpanel** - a new subpanel under Skeleton draws one row per native bone collection (honoring 4.1+ nesting: a parent collection becomes a labelled row of per-child select buttons), each row a button that selects the collection's bones plus an eye toggle bound to the collection's visibility. Selection and visibility only; assignment stays in the native panel.
- **E. Armature display mode** - expose `armature.display_type` (Octahedral / Stick / B-Bone / Envelope / Wire) so the whole rig's viewport draw style is one click from the panel.
- **F. Geometric custom shapes** - a small generated library of primitive widget meshes (circle, square, diamond, cube, sphere, arrow) and an operator that assigns one as the `custom_shape` of the active bone, the selected bones, or a whole collection, with basic scale / offset. The native `custom_shape` mechanism, the same Rigify uses, with a Proscenio-supplied shape set.
- **G. Per-collection bone color** - a color control that applies a palette (or custom triplet) to every bone in a collection in one click, since Blender has no native per-collection color.

## Open decisions

### 1. Connectivity flags: icon + tooltip, and which of the two is interactive

**Code anchors:** `apps/blender/panels/skeleton.py` (`PROSCENIO_UL_bones.draw_item`, lines ~137-149 - the current `flag_row.label(text=", ".join(flags))` building "connected" / "disconnected" / "relative" from `item.use_connect`, `item.parent`, `item.use_relative_parent`). `apps/blender/operators/selection.py` (`PROSCENIO_OT_select_bone_by_name` - the row-click operator pattern, `bl_description` tooltip, `armature_name` / `bone_name` props) for the toggle operator to mirror. Locked context: a Blender `layout.label` renders no tooltip, so any hovered explanation needs an operator button or a prop drawn with `emboss=False`.

**Question:** The text flags become icons; how does each gain a hover tooltip, and which flags are interactive? `Bone.use_connect` is read-only on the data bone (the writable `EditBone.use_connect` exists only in Edit mode, and connecting snaps the child head onto the parent tail - a geometric topology edit), whereas `Bone.use_relative_parent` is writable directly on the data bone in Pose / Object mode with no geometric side effect.

**Options:** (A) Both connectivity and relative are read-only info icons (operator with a dynamic `description`, no-op execute). (B) Connectivity is an info icon; relative parenting is a real toggle that flips `bone.use_relative_parent`. (C) Both are toggles, connectivity doing the Edit-mode round-trip with an undo + a warning tooltip.

**LOCKED (B), user-confirmed 2026-06-25:** connectivity (`LINKED` for connected, `UNLINKED` for a disconnected child) is information only - a no-op `proscenio.bone_flag_info` operator drawn `emboss=False` whose `@classmethod description` returns the per-flag explanation ("Connected to parent - head locked to parent's tail" / "Has a parent but its head moves free"), so the hover tooltip exists without touching topology; connect / disconnect stays in Blender's native Edit-mode workflow, since toggling it snaps the head and is a real geometry edit the panel should not hide. Relative parenting (`CON_CHILDOF`) is a live toggle: a `proscenio.toggle_bone_relative_parent` operator (armature + bone name) flips `bone.use_relative_parent` directly, `REGISTER`/`UNDO`, no Edit-mode round-trip, because it is a pose-inheritance flag with no geometric consequence. Option C (connectivity toggle) was rejected by the user: "vamos deixar o connected so como info mesmo."

### 2. Bone-list sort: hierarchy default, flat-alphabetical on the native A-Z toggle

**Code anchors:** `apps/blender/panels/_list.py` (`ProscenioListMixin.filter_items` - the shared filter that keeps source/collection order, which the bone list currently inherits unchanged). `apps/blender/core/outliner_view.py` (`outliner_sort_key`, `hierarchy_sort_key` - the precedent: A-Z on collapses every row into one name-keyed bucket so the tree drops to flat alphabetical, off keeps the parenting tree, and the caller zeroes the depth indent in the flattening mode). `apps/blender/panels/outliner.py` (`PROSCENIO_UL_sprite_outliner.filter_items` / `draw_item` - reads `use_filter_sort_alpha` and drops the indent). `apps/blender/panels/skeleton.py` (`PROSCENIO_UL_bones.filter_items` - currently only refreshes the IK scan then calls the mixin; `draw_item` computes `depth` by walking parents and indents).

**Question:** The bone list keeps source order always and ignores the UIList's A-Z toggle. To mirror the Outliner it needs a real bone hierarchy sort (depth-first, parent immediately before its children, so the indent reads as the tree) for the default and a flat alphabetical bucket when A-Z is on, dropping the indent. Where does the sort key live so it stays unit-testable without booting Blender?

**Options:** (A) New bpy-free `core/bone_view.py` with `bone_sort_key(bone, *, sort_alpha)` (depth-first ancestor-chain key off vs name-bucket on), called from `filter_items` via `compute_list_filter`, mirroring `core/outliner_view.py`. (B) Inline the sort in `skeleton.py` `filter_items` without a core module.

**LOCKED (A), 2026-06-25:** a new bpy-free `apps/blender/core/bone_view.py` carries `bone_sort_key(bone, *, sort_alpha)` and a `bone_depth` helper, exactly paralleling `core/outliner_view.py` so the same hierarchy/flat split is one tested pattern, not two. With A-Z off the key is the ancestor-name chain (root first, each parent immediately before its children) so the depth indent stays meaningful; with A-Z on every row collapses to a single name-keyed bucket for a flat alphabetical list and `draw_item` zeroes the indent (reading `use_filter_sort_alpha`, as the Outliner row does). `PROSCENIO_UL_bones.filter_items` switches from the bare mixin call to `compute_list_filter` with this `sort_key`, keeping the per-pass IK-scan refresh. A `core/test_bone_view.py` covers the two orderings against a small parent-indexed bone fixture.

### 3. Per-bone favorite: storage and chrome

**Code anchors:** `apps/blender/properties/object_props.py` (`ProscenioObjectProps`, `is_outliner_favorite: BoolProperty` line ~502 - the per-Object PropertyGroup to mirror). `apps/blender/operators/selection.py` (`PROSCENIO_OT_toggle_outliner_favorite` lines ~277-304 - the toggle operator pattern). `apps/blender/panels/outliner.py` (the star column in `draw_item` via `SOLO_ON` / `SOLO_OFF`, and the `outliner_show_favorites` header toggle + the favorites branch in `filter_items`). `apps/blender/properties/scene_props.py` (`outliner_show_favorites` BoolProperty - the filter toggle precedent).

**Question:** Objects store the favorite on `obj.proscenio`; bones have no Proscenio PropertyGroup. Where does a per-bone favorite live, and is it per-bone or per-collection?

**Options:** (A) New `ProscenioBoneProps` PropertyGroup registered as `bpy.types.Bone.proscenio`, `is_favorite: BoolProperty`. (B) A scene-level CollectionProperty of favorited bone names. (C) Reuse the native bone-collection star at collection granularity.

**LOCKED (A), user-confirmed 2026-06-25:** a new `apps/blender/properties/bone_props.py` defines `ProscenioBoneProps` with `is_favorite` and registers it as `bpy.types.Bone.proscenio`, mirroring the Object pattern so the favorite persists in the .blend and is per-armature. A `proscenio.toggle_bone_favorite` operator (armature + bone name) flips it; the bone list gains a `SOLO_ON` / `SOLO_OFF` star column and the Active Armature subpanel header gains a "Favorites" toggle (`skeleton_show_favorites` on the scene props) that the `filter_items` favorites branch reads, all copied from the Outliner. Per-bone, not per-collection (B was rejected as rename-fragile; C is the wrong granularity - a rigger pins individual control bones, not whole collections).

### 4. Rig UI subpanel: collection-driven layout, selection + visibility only

**Code anchors:** `apps/blender/operators/armature/authoring_ik.py` (`_ensure_controls_collection` line ~83 - existing `BoneCollection` use, the `armature.collections.new(...)` pattern). `apps/blender/panels/skeleton.py` (the subpanel registration block `_classes` and the `bl_parent_id = "PROSCENIO_PT_skeleton"` / `bl_order` pattern the new subpanel follows). `apps/blender/operators/selection.py` (`bone_select_only` / `bone_select_add` from `core.bpy_helpers._shared.bone_select`, the selection primitives the collection-select operator iterates). Native API: `armature.collections` (top-level roots), `armature.collections_all` (flat), `collection.children` / `collection.parent` (4.1+ nesting), `collection.bones`, `collection.is_visible`.

**Question:** A Rig UI panel maps each native bone collection to a button that selects its bones, with the nested collections (4.1+) producing the grouped Rigify-style rows. Does the panel honor the collection nesting for layout, and is it selection-only or does it also assign bones to collections?

**Options:** (A) One row per top-level collection; a collection with children becomes a labelled row of per-child select buttons, plus a per-collection eye toggle bound to `is_visible`; selection + visibility only, no assignment. (B) Also re-implement bone-to-collection assignment in the panel. (C) Flat one-button-per-collection, ignore nesting.

**LOCKED (A), user-confirmed 2026-06-25:** a new `PROSCENIO_PT_rig_ui` subpanel under Skeleton reads `armature.collections` and honors the native nesting - a top-level collection with children renders as a labelled row whose buttons are the child collections (the "Arm.L: IK | FK | Tweak" grouping straight from the 4.1+ tree), a childless top-level collection renders as a single-button row, and each row carries an eye drawn as `prop(collection, "is_visible")` (native tooltip, parent-hides-children inherited by Blender). Each select button runs a new `proscenio.select_bone_collection` operator (armature + collection name) that iterates `collection.bones` and `bone_select_add`s each in Pose / Edit mode (Object mode just activates), reusing the existing bone-select primitives. Selection and visibility only - assignment stays in Blender's native Bone Collections panel, since re-implementing it (B) duplicates native UI for no gain. With no nested or named collections (a bare QuickRig) the panel degrades to the flat button list, which is acceptable. The subpanel sits at `bl_order` 1 (immediately after Active Armature, before Pose Mode), tunable.

### 5. Armature display mode

**Code anchors:** `apps/blender/panels/skeleton.py` (`PROSCENIO_PT_armature.draw` - the Active Armature subpanel body, where the dropdown sits above or below the bone list). Native: `armature.data.display_type` enum (`OCTAHEDRAL` / `STICK` / `BBONE` / `ENVELOPE` / `WIRE`), the "Display As" of the native Viewport Display panel.

**Question:** Where does the armature-wide display dropdown sit, and is anything beyond `display_type` worth surfacing?

**LOCKED 2026-06-25:** a single `layout.prop(target.data, "display_type", text="Display As")` row in the Active Armature subpanel (above the bone list, with the bone count). Armature-wide, native, zero new code beyond the row. The other Viewport Display toggles (Names, Shapes, Bone Colors, In Front) stay in Blender's native panel for now; only the display-type enum, the one a Proscenio user changes while authoring, is surfaced - revisit if the others are missed.

### 6. Per-collection bone color

**Code anchors:** `apps/blender/operators/selection.py` / the new `proscenio.select_bone_collection` (the collection-iteration twin this batches over). Native: `bone.color.palette` (`DEFAULT` / `THEME01`..`THEME15` / `CUSTOM`) and `bone.color.custom.normal` / `.select` / `.active`; color is per data bone (shared) with an optional `pose.bones[name].color` override. Confirmed via the 4.0 bone-collections upgrade notes: there is no per-collection color property; "Copy to Selected" is the native batch path.

**Question:** Blender has no per-collection color. A Proscenio operator colors every bone in a collection at once. Does it set a theme palette index or a custom triplet, and does it write the data-bone color or the pose-bone override?

**Options:** (A) Theme palette enum applied to `bone.color.palette` on every data bone in the collection (pose override left `DEFAULT`). (B) Custom color picker writing `bone.color.custom`. (C) Both, palette default with a custom escape hatch.

**LOCKED (C), 2026-06-25:** a `proscenio.color_bone_collection` operator (armature + collection name + a palette enum, plus an optional custom triplet when palette is `CUSTOM`) iterates `collection.bones` and sets each data bone's `color.palette` (and `color.custom.*` when custom), leaving the pose-bone override at `DEFAULT` so the color is consistent across pose. Writing the data-bone color, not the pose override, because the spec wants one stable color per control group, not a per-pose tint. The Rig UI row is the natural host (a color swatch beside each collection's select button), but the operator is panel-agnostic. Palette is the default affordance with a custom escape hatch, matching Blender's own bone-color UI.

### 7. Geometric custom shapes: shape library, assignment scope, persistence

**Code anchors:** no existing Proscenio code - new. Native: `pose_bone.custom_shape` (a Mesh Object drawn in place of the bone in Pose mode), `custom_shape_scale_xyz`, `custom_shape_translation`, `custom_shape_rotation_euler`, `custom_shape_transform`, `use_custom_shape_bone_size`. Precedent: Rigify generates `WGT-` widget meshes and assigns them through this same native API; the third-party Bone Widget addon is the canonical "primitive shape library + assign" tool this mirrors at a smaller scope. `apps/blender/operators/armature/authoring_ik.py` for the controls-collection pattern (where generated widgets could be parked).

**Question:** Custom shapes are native, but Blender ships no shape library - the mesh must be supplied. This is the meatiest sub-feature: which primitive shapes ship, how are the widget meshes generated and stored so they persist in the .blend without cluttering the scene, what is the assignment scope (active bone / selected / collection), and how much transform control is exposed?

**Options (shape source):** (A) Generate primitive widget meshes on demand from code (bmesh) into a hidden collection / data-block, deduped by name. (B) Ship a .blend asset library of widgets and link them. (C) Author shapes by hand per project.

**Options (assignment scope):** active bone only / active + selected / whole collection (the collection-iteration twin again).

**LOCKED 2026-06-25, with two sub-points to settle in TODO:** shapes are generated on demand from code (A) - a `core` widget-builder makes a small 2D primitive set (circle, square, diamond, line, triangle, arrow) as Mesh data-blocks named `WGT-proscenio-<shape>`, created once and reused (deduped by name), parked in a dedicated hidden bone-widget collection so they persist in the .blend and never render in the scene, mirroring how Rigify keeps its `WGT-` meshes. The set is deliberately flat - Proscenio is a 2D pipeline, so 3D widgets (cube, sphere) are out of scope; the shapes are planar outlines that read on the picture plane (user-confirmed 2026-06-25, dropping cube/sphere for line/triangle). A `proscenio.assign_bone_shape` operator takes a shape id and a scope (active / selected / collection, the same scope ladder the color and select operators use) and sets `custom_shape` on each target pose bone, with `custom_shape_scale_xyz` and `custom_shape_translation` exposed as operator props for a basic fit. Generated-from-code over a shipped asset library (B) because a handful of bmesh primitives is less to ship and version than a .blend, and the shapes are simple geometric outlines. Two sub-points deferred to TODO planning, not blocking the lock: (i) whether the outlines are wire-only meshes or filled (the planar set is fixed); (ii) whether the assignment UI is a row in the Rig UI subpanel, a dedicated Bone Display subpanel, or a popup - leaning a dedicated subpanel since it pairs with the display-type and color controls.

### 8. Shared collection-iteration primitive

**Code anchors:** the three new operators - `proscenio.select_bone_collection` (decision 4), `proscenio.color_bone_collection` (decision 6), `proscenio.assign_bone_shape` collection scope (decision 7) - all walk `collection.bones`.

**LOCKED 2026-06-25:** a single bpy helper `iter_collection_bones(armature, collection_name)` (or a small `for_each_bone_in_collection(armature, name, fn)`) in `core/bpy_helpers` is the one place that resolves a collection by name on an armature and yields its bones, so the select / color / shape operators share one resolution + missing-collection guard rather than re-deriving it three times. Lands with decision 4 (the first consumer).

## Verdict summary

LOCKED 2026-06-25, all eight decisions resolved, single spec per the user's call to keep custom shapes in. Bone-list polish: connectivity becomes info-only icons with tooltips (decision 1, user-confirmed), relative parenting becomes a clean `use_relative_parent` toggle, the list gains the Outliner's hierarchy/flat-alpha sort via a new tested bpy-free `core/bone_view.py` (decision 2) and a per-bone favorite on a new `bpy.types.Bone.proscenio` PropertyGroup with a star column and Favorites filter (decision 3). New surfaces: a collection-driven Rig UI subpanel that honors 4.1+ nesting for grouped select buttons plus per-collection visibility toggles, selection + visibility only (decision 4); an armature-wide `display_type` dropdown (decision 5); a per-collection color operator (decision 6); and a generated geometric custom-shape library with a scoped assign operator (decision 7), its primitive set and host UI the only sub-points left for TODO. A shared `iter_collection_bones` helper backs the three collection operators (decision 8). Size L: one new core module + its test, one new properties module (Bone PropertyGroup), one new panel (Rig UI) plus edits to the bone UIList and Active Armature subpanel, four new operators (relative toggle, bone favorite, collection select, collection color, shape assign) and the no-op flag-info operator, plus the widget-mesh builder. The interactive HTML mockup of all seven surfaces lives at [interaction-mockup.html](interaction-mockup.html). See TODO.md (to be written after STUDY review).
