# Spec 079: Per-animation slot swaps (visibility-driven, multi-animation)

A slot swap authored in Proscenio today lands as an integer `proscenio_slot_index` keyed on the slot Empty. The bone-animation writer reads *every* action in the file and emits one Godot animation per action name; the slot-animation writer reads *only* the Empty's one currently-assigned action, because that index path (`["proscenio_slot_index"]`) is identical on every slot and a bare action datablock cannot say which slot it targets. So a slot can carry exactly one swap timeline for the whole export, the swap is invisible while scrubbing in Blender (nothing drives child visibility from the index), and "no attachment visible" is inexpressible. A character with `idle` (no weapon), `attack_chicken`, and `attack_staff` cannot hold a per-animation weapon state.

This spec replaces the index-on-the-Empty authoring model with **direct visibility keyframes on the attachment meshes**. Keying an attachment's visibility (`hide_render` / `hide_viewport`) previews natively in Blender on every supported version, expresses "none visible" for free (hide them all), and maps one-to-one onto the Godot runtime, which already animates each attachment's `visible`. The exported `slot_attachment` track and the `.proscenio` schema do not change - only which Blender data the writer reads. On Blender 4.4+ the visibility and the bone motion co-locate in one slotted action per animation; on 4.2 they live in same-named separate actions the export merges by name, so the feature works everywhere and only the datablock tidiness differs.

## Why now

- The maintainer hit it directly authoring `firebound_guy`: keyframing a slot swap created a second action (`slot_hand.RAction`), the swap did not show in the viewport, and the three-animation weapon-state workflow (idle no weapon; chicken / staff per attack, with the slot's bone animated in each armed clip) is not expressible because only one slot action exports.
- The Godot runtime already drives per-attachment `visible` ([animation_builder.gd](../../apps/godot/addons/proscenio/builders/animation_builder.gd) `_add_slot_attachment_tracks`) and the `slot_attachment` track type already ships (spec 042 / 046 / 051). Emitting that track from visibility keyframes instead of from an index is a change to the Blender authoring side only, with no schema or Godot-builder churn.

## Current state

- **Authoring**: `keyframe_slot_attachment` ([apps/blender/operators/slot/attachment.py](../../apps/blender/operators/slot/attachment.py)) resolves the chosen attachment to an index against an append-only name snapshot (`PROSCENIO_SLOT_ATTACHMENT_ORDER`), writes `empty["proscenio_slot_index"]`, `keyframe_insert`s it CONSTANT, and thereby creates the Empty's own `animation_data.action`. This whole index-on-the-Empty path is what this spec replaces.
- **Bone writer** ([animations.py](../../apps/blender/exporters/godot/writer/animations.py)): `build_animations` iterates `iter_actions()` = every `bpy.data.actions`; each becomes one `Animation(name=action.name)`. Bone tracks resolve globally (`pose.bones["name"]` is armature-resolvable regardless of the owning action), which is why global iteration works for bones but not for slots.
- **Slot writer** ([slot_animations.py](../../apps/blender/exporters/godot/writer/slot_animations.py)): `build_slot_animations` reads only `obj.animation_data.action` per slot Empty and projects the `proscenio_slot_index` fcurve into a `slot_attachment` track (one key per index, `attachment` = the name at that index). `merge_slot_animations_into` then merges that into a same-named bone animation. The merge-by-name and the track shape are kept; the index source is replaced.
- **Animation panel** ([animation.py](../../apps/blender/panels/animation.py)): lists `bpy.data.actions` verbatim and `set_active_action` assigns the clicked action to the Skeleton-picked armature - so a slot/visibility action shows as a rig animation and clicking grafts it onto the armature.
- **Godot default** ([slot_builder.gd](../../apps/godot/addons/proscenio/builders/slot_builder.gd)): `_effective_default` falls back to the first attachment when the default names nothing, so a slot never rests blank.
- **Godot runtime, per-attachment visibility already the model** ([animation_builder.gd](../../apps/godot/addons/proscenio/builders/animation_builder.gd)): `_add_slot_attachment_tracks` emits one `visible` track per attachment child; a key naming a child that does not exist hides all of them. A "none" key is already representable in the runtime - the writer just never emits one.
- **Layered-action reader already present** ([action_fcurves.py](../../apps/blender/core/_shared/action_fcurves.py)): flattens fcurves across legacy `fcurves` and 4.4+ `layers > strips > channelbags`, so the writer already tolerates slotted actions (without yet distinguishing which slot/datablock a curve belongs to).
- **Version floor**: `blender_version_min = "4.2.0"` ([blender_manifest.toml](../../apps/blender/blender_manifest.toml)); slotted (multi-datablock) actions are 4.4+, so they cannot be a hard requirement.

## Decisions (locked)

| # | Question | Call |
| --- | --- | --- |
| D1 | What property carries the swap, and how do multiple animations coexist? | **Direct visibility keyframes on the attachment meshes; keep `min = 4.2` and degrade gracefully.** Retire the `proscenio_slot_index` idprop. The artist keys each attachment mesh's visibility (`hide_render`, mirrored to `hide_viewport` for the viewport); the writer reads those keyframes per slot (owner is intrinsic - each mesh is its own datablock) and emits the same `slot_attachment` track. Native viewport preview on every version; "none visible" is just all-hidden. On Blender 4.4+ the bone motion and the attachment visibility co-locate in one slotted action per animation (both the armature and the meshes bind `animation_data.action` to that animation's action, each on its own slot); on 4.2 they live in same-named separate actions merged by name at export. No version bump - 4.2 keeps preview and export, only losing the single-datablock tidiness. |
| D2 | What should the Animation panel show now that visibility actions exist alongside rig actions? | **List exported animations by name (dedup), not raw action datablocks.** The panel shows `idle` / `attack_chicken` / `attack_staff` once each, regardless of how many datablocks (rig plus per-mesh visibility) compose them - matching what the export already merges by name and how the artist thinks. Clicking selects the whole animation. `set_active_action` no longer grafts a visibility-only action onto the armature. |
| D3 | How does a slot swap know which animation it belongs to? | **Follow the active animation by default, with an explicit override picker.** The swap inherits the name of the active animation (the rig's active action, i.e. the one selected in the D2 panel), so authoring the swap needs no extra step - you pick the animation by making it active, which you already do to animate it. An override dropdown in the Active Slot panel lets the swap target a different animation when needed. |
| D4 | How is "no attachment visible" (idle, no weapon) expressed? | **A first-class "(none)" state, free from the visibility model.** With direct visibility there is no sentinel and no writer/Godot change: keying all attachments hidden at a frame *is* "none". The Active Slot panel gains a "(none) / hide all" keyable row so the state is authorable and keyframable like any attachment, and `slot_builder._effective_default` gains an explicit-blank path so a slot can also *rest* with nothing shown, not only hide mid-clip. |
| D5 | How is the swap previewed in Blender? | **Natively - no handler.** Keyframed object visibility previews on scrub in every version, so the `frame_change_post` handler the index model would have needed is dropped entirely. The viewport matches the Godot runtime for free. |

The "animate the slot's bone in the armed clips" part needs no work: that is ordinary `bone_transform` on the armature action for `attack_chicken` / `attack_staff`, and the slot follows the bone through its Bind-to-Bone constraint. Only the attachment selection per animation is the gap this spec closes.

## Resolved calls (locked during the 2026-07-09 analysis pass)

- **R1 - visibility property + sync.** The keyframe operator keys `hide_viewport` **and** `hide_render` in lockstep (a single "show only this attachment" action inserts keys on every sibling); the writer reads `hide_render` as the export truth (render intent maps to Godot `visible`), while `hide_viewport` guarantees the viewport preview. Keying only `hide_render` would leave the viewport un-previewed (defeating the point); keying only `hide_viewport` would work but skip the render-intent truth. The `slot_swap` fixture already sets both for the static hidden state ([build_blend.py:267](../../packages/fixtures/slot_swap/build_blend.py)), so this is an existing pattern.
- **R2 - mutual exclusivity.** The output stays one-attachment-per-key: `Key.attachment` is a single name and the Godot builder sets `child.visible = (name == attachment)`, so keeping the schema keeps exclusivity in the exported track. The writer collapses authored visibility per frame: 0 visible emits a "none" key, 1 visible emits that attachment, 2+ visible emits the first by child sort order (deterministic) and the export validator raises a warning (lazy + inline, per `decisions.md`). Attachment layering is not a slot concern (slots are exclusive swaps by design) - two-at-once belongs in separate slots.
- **R3 - migration off `proscenio_slot_index`.** Clean cut, no writer dual-read: the project is pre-launch (v0.9.1, no external authored-blend base), and only `slot_swap` / `slot_cycle` key the index for animation (`mixed_feature` has no slot animation). Migrate those two build scripts to the visibility model, remove the index reader from the writer, and ship a one-shot converter operator for in-flight authored blends (the maintainer's `firebound_guy`) so no hand-re-authoring is lost.
- **R4 - slotted (4.4+) vs same-name (4.2), and the double-count trap.** On 4.4+ the attachment mesh and the armature share one "idle" action datablock (distinct slots), and `action_fcurves` flattens every channelbag - so a slot writer using that flattened view would read every mesh's visibility curves while processing one, double-counting. The slot writer therefore reads visibility **per attachment mesh, scoped to that mesh's own `animation_data`** (its `action_slot` channelbag on 4.4+, its dedicated action on 4.2), never the flattened `action_fcurves`. Invariant guard: a golden built the 4.2 way and the 4.4 way must export byte-identical (add that golden pair).
- **R5 - index-drift guard retirement.** Direct visibility keys by object identity (the mesh itself), so deleting an attachment drops its keys with no index to remap - the drift class is gone. Remove the `PROSCENIO_SLOT_ATTACHMENT_ORDER` snapshot and its append-only merge, and close the gated `keyframe-slot-index-drift` item (spec 076). The only consumers are the index model being replaced ([cp_keys.py](../../apps/blender/core/_shared/cp_keys.py), [slot_animations.py](../../apps/blender/exporters/godot/writer/slot_animations.py), [attachment.py](../../apps/blender/operators/slot/attachment.py)).

## Out of scope / follow-ons

- **Skins (spec 059)** - named cross-slot attachment *sets* (one switch changes many slots) are 059's job and need a Godot runtime layer. 079 is the per-slot, per-animation visibility *timeline* that 059 builds on. No overlap in surface.
- **Schema / format / Godot builder** - all unchanged. The `slot_attachment` track type, the `Slot` model, `format_version=1`, and the Godot per-attachment `visible` tracks stay; this spec only changes which Blender data the writer reads and how the panel presents animations. The one Godot-side edit is `slot_builder._effective_default`'s explicit-blank path for D4.
- **Per-key interpolation mixing** - slot swaps stay hard-cut (CONSTANT authoring intent / NEAREST in Godot); nothing here revisits it.
- **A Godot runtime `set_attachment(name)` API** - runtime attachment control is 059's runtime-layer decision; 079 ships only the animation-driven swap, which needs no runtime.
