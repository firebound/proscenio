# Spec 080: Element bone binding - rest-transform fidelity and constraint-first authoring

A sprite element bone-parented in Blender renders wrong in Godot whenever the bone's rest transform is not identity. The exporter emits only the bone *name* ([sprite_element.py](../../apps/blender/exporters/godot/writer/sprites/sprite_element.py) via [resolve_sprite_bone](../../apps/blender/exporters/godot/writer/sprites/_common.py)); the importer adds the Sprite2D as a child of the Bone2D with an identity local transform ([sprite_builder.gd](../../apps/godot/addons/proscenio/builders/sprite_builder.gd)). The sprite therefore inherits the bone's full rest rotation and anchors at the bone head - but in Blender the keep-transform bone parent ([bone_attach.py](../../apps/blender/core/bpy_helpers/sprite/bone_attach.py)) preserves the authored world placement, storing the sprite-vs-bone relationship in the object basis that the export then throws away. In `firebound_guy`: the `fire` and `eye.glow` bones carry a -90 degree rest rotation, so their sprites render lying sideways; the `char__eye__eyeball` origin sits (29.4, -12.0) px away from its bone head, so the eyeball renders shifted and the (correctly baked) iris mesh visibly pops out of it mid-animation. Rigid meshes are NOT affected (an implementation-time correction to this study's first draft): the writer already bakes a rigid bone-parented mesh's vertices bone-local ([mesh_element.py](../../apps/blender/exporters/godot/writer/sprites/mesh_element.py) rotates them into the bone frame), so the identity local transform under the Bone2D composes correctly - the sprite element is the one element kind that ships placement-blind.

This spec fixes the data flow **and** unifies the element/slot bone-binding mental model. Fix: the sprite element carries its rest transform in the document and the Godot builders convert it to parent-local against whatever the element parents under (bone, slot anchor, or skeleton root). Refactor: **one binding model across elements and slots** - elements (sprite and rigid mesh alike) adopt the slot's Bind-to-Bone authoring (a Child Of constraint from the Proscenio panel - clear, one-click, non-destructive), the raw bone parent stays supported as a power-user fallback, and the binding state itself is simplified (constraint becomes the single source of truth, retiring the `slot_bone` triple storage and the `field_inert` state). After the fix the follow shapes are semantically identical in both engines, which is exactly what makes one mental model coherent. The only per-kind difference that remains is where placement lives in the document, and it is inherent, not a binding difference (R6): a mesh's placement is baked into its absolute vertices, a sprite's lives in the new rest-transform fields - the builder consumes both through the same formula.

## Why now

- The maintainer hit it authoring `firebound_guy` (2026-07-12): the fire flame rendered rotated 90 degrees left, the eye glow landed wrong, and around t=4s the iris jumped out of the eyeball. The diagnostic session confirmed the exported bone animation values match Blender's posed bones exactly - the divergence is entirely the discarded element rest transform.
- The sprite attach operator's own description documents the competing models as a caveat: "For a bone in the picture plane the sprite rotates with the bone rest - use a slot for a flat follow" ([bone_parent.py](../../apps/blender/operators/sprite/bone_parent.py)). The maintainer has to remember that an element's bone parent behaves differently from a slot's bind. Once the rest transform is carried, that behavioral difference disappears - the remaining difference is pure authoring ergonomics, where the constraint flow (one click in the panel, no pose-mode round trip, no snap) is strictly better.
- Native bone-parent authoring in Blender is genuinely convoluted (pose mode to select the bone, back to object mode, Ctrl+P - or the Relations panel with its default snap), while Bind Slot to Bone is already the proven one-click shape (spec 042).

## Current state

- **Blender authoring, sprites**: [parent_to_bone_keep_world](../../apps/blender/core/bpy_helpers/sprite/bone_attach.py) authors a real `parent_type == "BONE"` parent keep-transform; the operator pair lives in [bone_parent.py](../../apps/blender/operators/sprite/bone_parent.py). The object basis cancels the bone rest (tail anchor + rest orientation), so authoring looks right in Blender for any bone orientation.
- **Blender authoring, slots**: [bone_follow.py](../../apps/blender/core/bpy_helpers/slot/bone_follow.py) authors object-parent + a `Child Of` constraint (`Proscenio Slot Follow`) whose `inverse_matrix` cancels the bone rest - the Blender twin of the Godot slot anchor. It maintains a four-state shape taxonomy (`constraint` / `bone_parent` / `field_inert` / `none`), a legacy bone-parent conversion to avoid double-driving, and the `slot_bone` field written PG + Custom Property dual ([_write_slot_bone](../../apps/blender/core/bpy_helpers/slot/bone_follow.py)) that the writer reads ([slots.py](../../apps/blender/exporters/godot/writer/slots.py)). Net: one binding stored in three places (field, CP mirror, constraint) plus one legacy shape.
- **Export**: [build_sprite](../../apps/blender/exporters/godot/writer/sprites/sprite_element.py) emits `bone`, frame metadata, flips, and a pivot `offset` measured in world screen coordinates - no position, no rotation, no scale. `_compute_sprite_offset`'s world-frame measurement is itself only correct while the Godot node renders unrotated. The skeleton and animation writers are verified correct (see R1).
- **Import**: [sprite_builder.gd](../../apps/godot/addons/proscenio/builders/sprite_builder.gd) `routing.node.add_child(sprite)` with no transform - identity local under the Bone2D. [mesh_builder.gd](../../apps/godot/addons/proscenio/builders/mesh_builder.gd) routes a rigid (unskinned) mesh the same way, on top of absolute baked vertices. [slot_builder.gd](../../apps/godot/addons/proscenio/builders/slot_builder.gd) is the correct pattern: `node.transform = bone_in_skeleton.affine_inverse()` derived from the live rest globals at build time.
- **Validation**: no check flags an object driven by both a bone parent and a follow constraint (double-drive - the only constraint-aware check today is IK bake, [ik_bake.py](../../apps/blender/core/validation/checks/ik_bake.py)), and no check detects a follow whose stored inverse no longer cancels the current bone rest (stale after a rig edit; identically applicable to the keep-transform parent basis).
- **Latent bind-at-pose divergence**: [bind_slot_to_bone](../../apps/blender/core/bpy_helpers/slot/bone_follow.py) computes the inverse from `pose_bone.matrix` - the *posed* matrix. Binding on a posed rig cancels that pose instead of the rest; the Godot anchor always cancels the rest. Silent Blender-vs-Godot divergence.

### Diagnosis evidence (2026-07-12 session, `firebound_guy`)

Exported animation values match Blender's posed bone heads exactly (frame 100 / t=4.125s: `eye.eyeball` (19.262, -639.616) both sides; `eye.iris` (104.246, -643.769) both sides) - the animation writer is not at fault. The two failing components of the discarded rest transform:

| component | evidence | visible symptom |
| --- | --- | --- |
| rotation | `fire` and `eye.glow` bone rest rotation -1.570796 in the doc; sprites inherit it (identity local under Bone2D) | flame and glow render rotated -90 degrees; `eye.eyeball` (rest rotation 0.0) coincidentally unaffected |
| position | `char__eye__eyeball` world origin (35.845, -651.576) vs bone head (6.46, -639.616): a (29.4, -12.0) px authored gap the doc never carries | eyeball renders shifted left/down; the absolutely-baked iris mesh pops out of it at iris excursion peaks (~t=4s) |

## Decisions (locked)

| # | Question | Call |
| --- | --- | --- |
| D1 | How does the document carry a sprite's placement? | **Absolute (skeleton-space) rest transform on the sprite element**: optional `position` [x, y] px, `rotation` rad, `scale` [sx, sy] fields, emitted from the object's rest `matrix_world` through the existing Godot projection ([godot_export_math.py](../../apps/blender/core/godot_export_math.py)). The builder converts to parent-local at build time: `local = parent_global_in_skeleton^-1 * rest`, the same live-rest-globals technique the slot anchor already uses. Absolute rather than bone-local because it is frame-agnostic to routing - the same fields are correct under a Bone2D, under a slot anchor (which cancels the bone rest), or at the skeleton root - and it matches the document convention that mesh vertices are absolute screen space. Absent fields default to today's identity-local behavior, so older documents parse unchanged. |
| D2 | Rigid mesh routed under a Bone2D? | **Already correct - no change (revised during implementation).** The study's first draft assumed rigid mesh vertices bake absolute and double-transform under a Bone2D; the writer in fact bakes a rigid bone-parented mesh's vertices BONE-LOCAL ([mesh_element.py](../../apps/blender/exporters/godot/writer/sprites/mesh_element.py), the spec 039 in-plane convention), so the identity local under the Bone2D composes correctly today. Skinned, slot-routed, and root-routed meshes bake absolute and their parents contribute identity. The mesh gains no transform fields because its placement home is the baked vertices (R6). |
| D3 | The pivot `offset` under a rotated node? | **Pull the measured gap back into the node's local frame.** `Sprite2D.offset` applies before the node transform, so the world-frame measurement breaks the moment the node carries rotation or scale. The world-projected gap is rotated by the negated rest rotation and divided by the rest scale (implementation note: this generalized form, rather than a raw local-bounds read, keeps both quad authoring conventions working - PSD planes are local-XZ flat, hand-made planes are local-XY stood up 90 degrees). For the untouched common case (no rotation, unit scale) the value is exactly the old measure, and the flip-sign cancel of spec 076 is preserved. Scale exports as magnitudes with the existing flip flags so the mirror is never counted twice. |
| D4 | Authoring model for element bone binding? | **Constraint-first, parent fallback - for every element kind.** The attach operator (widened from sprite-only to any rigid element: sprite or unskinned mesh) authors object-parent + `Child Of` (via the shared core, D6) instead of a real bone parent - same one-click panel flow as Bind Slot to Bone, non-destructive, no pose-mode round trip. One binding model across elements and slots. The raw bone parent (and the vertex-group convention) stays a supported power-user fallback. A skinned mesh binds via weights, not a follow - it is outside the binding surface (R5). Export binding resolution precedence: follow constraint > `parent_bone` > first vertex group. The operator-description caveat ("use a slot for a flat follow") retires - after D1 both shapes render identically. |
| D5 | Where does a binding live (source of truth)? | **The constraint itself** (`target` + `subtarget`), readable headless from the .blend with no addon. The `slot_bone` field retires as an authority: `_write_slot_bone`, the PG proxy getter/setter, and the CP mirror go; the writer reads the constraint first and keeps the field + `parent_bone` as read-fallbacks for existing files. The `field_inert` state (data says bound, viewport does not follow) can no longer occur; the shape taxonomy drops to `constraint` / `bone_parent` / `none`. |
| D6 | Where does the bind machinery live? | **One shared bone-follow core** in `core/bpy_helpers/_shared/` (bind / unbind / shape detection / stale check / picture-plane guard), parametrized by constraint name. `slot/bone_follow.py` and the sprite attach helper become thin wrappers. Constraint names stay distinct (`Proscenio Slot Follow` kept for slots - no migration churn; `Proscenio Sprite Follow` for sprites) so detection stays per-kind while the machinery is single-home. |
| D7 | The inverse correctness + staleness? | **Bind computes the inverse from the rest matrix** (`bone.matrix_local`, not `pose_bone.matrix`) so binding on a posed rig cannot bake a pose-cancel that Godot will never reproduce; the operator warns when the target bone is posed at bind time. A new validation check recomputes the expected inverse from the current rest and warns on mismatch (rig edited since bind, or rig object moved) with a one-click Rebind quickfix. The check covers slots and sprites through the shared core. |
| D8 | Double-drive detection? | **New validation check** (today: none): an object carrying both a BONE parent and a Proscenio follow constraint warns - the viewport double-applies the bone and the export has to pick one source. Quickfix: drop the bone parent keep-world (the existing conversion, promoted into the shared core). |

## Resolved calls

- **R1 - animation writer verified correct.** The exported `bone_transform` keys were compared against headless Blender's posed world bone heads at every keyframe time; they match to the sixth decimal. No animation-side work in this spec.
- **R2 - why not fix import-side only (like slots)?** The importer cannot recover data the document never carried: the slot anchor can cancel rest because its attachments bake absolute vertices, but a rigid sprite bakes nothing - its placement lives only in the Blender object transform. The exporter has everything at hand; the document must carry it.
- **R3 - migration for in-flight rigs.** The D1 fix alone repairs `firebound_guy`'s render with zero re-authoring (the bone-parent fallback keeps exporting). A one-click "Convert to constraint follow" operator migrates a bone-parented sprite to the D4 shape keep-world, for rigs wanting the unified model.
- **R4 - both mechanisms are motion-identical.** Bone parent keep-transform and Child Of with a rest inverse compose to the same matrix (`pose @ rest^-1 @ authored_world`), so D4 changes ergonomics and state bookkeeping only - no fixture or golden churn from the authoring swap itself (the fixtures that author bone parents keep exporting identically through the fallback).
- **R5 - skinned meshes untouched.** Weight-deformed Polygon2Ds (the `weights` path) parent as skeleton siblings and deform per-vertex; they carry no node-transform binding and are out of this bug's family.
- **R6 - why the sprite element gains schema fields and the mesh element does not.** Not a binding difference - binding, authoring, and the builder formula are identical for both. The difference is where placement lives in the document: a mesh element bakes absolute skeleton-space vertices (its rest transform is identity by construction; transform fields would be always-zero or double-count), while a sprite element ships no geometry - its placement lives only in the node transform, which is exactly the data the doc never carried. D1 gives the sprite the placement home the mesh always had. Un-baking mesh vertices to local + a node transform would be a format rewrite with no benefit (skinning also consumes skeleton-space vertices).

## Out of scope / follow-ons

- **Skinned mesh skinning path** - sibling parenting, weight resolution, and vertex baking are unchanged (R5).
- **Animation writer / schema animation tracks** - verified correct (R1); `bone_transform` track shape unchanged.
- **Slot anchor semantics in Godot** - [slot_builder.gd](../../apps/godot/addons/proscenio/builders/slot_builder.gd) stays as-is; the new shared parent-local helper reuses its formula rather than changing it.
- **Skins (spec 059)** - cross-slot attachment sets are unrelated to binding mechanics.
- **A generic constraint passthrough** - exporting arbitrary Blender constraints stays out; the follow constraint is authoring-side machinery, not document data.
